Codebase Design

程式碼庫設計

Design deep modules: a lot of behaviour behind a small interface, placed at a clean seam, testable through that interface. Use this language and these principles wherever code is being designed or restructured. The aim is leverage for callers, locality for maintainers, and testability for everyone.

設計深模組：小介面背後有大量行為、放在乾淨的接縫上、可以透過那個介面測試。在任何程式碼被設計或重構的地方使用這套語言與這些原則。目標是讓呼叫者獲得槓桿收益、維護者獲得局部性、所有人獲得可測試性。

Glossary

詞彙表

Use these terms exactly — don't substitute "component," "service," "API," or "boundary." Consistent language is the whole point.

精確使用這些術語——不要替換成「component」「service」「API」或「boundary」。一致的語言就是重點。

Module — anything with an interface and an implementation. Deliberately scale-agnostic: a function, class, package, or tier-spanning slice. Avoid: unit, component, service.

模組——任何有介面與實作的東西。刻意地與規模無關：一個函式、類別、套件，或橫跨層級的切片。Avoid: unit、component、service。

Interface — everything a caller must know to use the module correctly: the type signature, but also invariants, ordering constraints, error modes, required configuration, and performance characteristics. Avoid: API, signature (too narrow — they refer only to the type-level surface).

介面——呼叫者要正確使用模組所需知道的一切：型別簽名，也包括不變量、順序約束、錯誤模式、必要的設定，與效能特徵。Avoid: API、signature（太窄——它們只指型別層級的表面）。

Implementation — what's inside a module, its body of code. Distinct from Adapter: a thing can be a small adapter with a large implementation (a Postgres repo) or a large adapter with a small implementation (an in-memory fake). Reach for "adapter" when the seam is the topic; "implementation" otherwise.

實作——模組裡面的東西，它的程式碼本體。與轉接器區別：一個東西可以是小轉接器配大實作（Postgres repo），或大轉接器配小實作（記憶體中的假物件）。當主題是接縫時用「轉接器」；其他情況用「實作」。

Depth — leverage at the interface: the amount of behaviour a caller (or test) can exercise per unit of interface they have to learn. A module is deep when a large amount of behaviour sits behind a small interface, shallow when the interface is nearly as complex as the implementation.

深度——介面上的槓桿收益：呼叫者（或測試）每學習一單位介面所能行使的行為量。當大量行為藏在一個小介面後面時，模組是深的；當介面幾乎跟實作一樣複雜時是淺的。

Seam (Michael Feathers) — a place where you can alter behaviour without editing in that place; the location at which a module's interface lives. Where to put the seam is its own design decision, distinct from what goes behind it. Avoid: boundary (overloaded with DDD's bounded context).

接縫 (Michael Feathers)——一個你可以不用在原地編輯就能改變行為的地方；模組介面所在的位置。接縫放哪裡本身是一個設計決策，與放在它後面的是什麼是兩回事。Avoid: boundary（與 DDD 的 bounded context 過載）。

Adapter — a concrete thing that satisfies an interface at a seam. Describes role (what slot it fills), not substance (what's inside).

轉接器——在接縫處滿足某個介面的具體東西。描述角色（它填補什麼槽位），不是實體（裡面是什麼）。

Leverage — what callers get from depth: more capability per unit of interface they learn. One implementation pays back across N call sites and M tests.

槓桿收益——呼叫者從深度得到的：每學習一單位介面獲得更多能力。一份實作在 N 個呼叫點與 M 個測試之間回本。

Locality — what maintainers get from depth: change, bugs, knowledge, and verification concentrate in one place rather than spreading across callers. Fix once, fixed everywhere.

局部性——維護者從深度得到的：變更、bug、知識與驗證集中在一個地方，而不是散落在呼叫者之間。修一次，處處修好。

Deep vs shallow

深 vs 淺

Deep module = small interface + lots of implementation:

深模組 = 小介面 + 大量實作：

┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘

┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘

Shallow module = large interface + little implementation (avoid):

淺模組 = 大介面 + 少許實作（避免）：

┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘

┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘

When designing an interface, ask:

設計介面時問：

  • Can I reduce the number of methods?
  • Can I simplify the parameters?
  • Can I hide more complexity inside?
  • 我能減少方法數量嗎？
  • 我能簡化參數嗎？
  • 我能把更多複雜度藏在裡面嗎？

Principles

原則

  • Depth is a property of the interface, not the implementation. A deep module can be internally composed of small, mockable, swappable parts — they just aren't part of the interface. A module can have internal seams (private to its implementation, used by its own tests) as well as the external seam at its interface.
  • The deletion test. Imagine deleting the module. If complexity vanishes, it was a pass-through. If complexity reappears across N callers, it was earning its keep.
  • The interface is the test surface. Callers and tests cross the same seam. If you want to test past the interface, the module is probably the wrong shape.
  • One adapter means a hypothetical seam. Two adapters means a real one. Don't introduce a seam unless something actually varies across it.
  • 深度是介面的屬性，不是實作的屬性。 深模組可以在內部由小而可模擬、可替換的部件組成——它們只是不是介面的一部分。模組可以同時有內部接縫（實作私有、供自己的測試使用）以及位於其介面上的外部接縫。
  • 刪除測試。 想像刪掉這個模組。如果複雜度消失，它只是個轉送層。如果複雜度在 N 個呼叫者之間重現，它在賺自己的住宿費。
  • 介面就是測試表面。 呼叫者和測試跨越同一個接縫。如果你想測試到介面之後，模組大概形狀錯了。
  • 一個轉接器意味著假設性接縫；兩個轉接器意味著真實接縫。 除非有什麼東西真的跨越它而變化，否則不要引入接縫。

Designing for testability

為可測試性設計

Good interfaces make testing natural:

好介面讓測試很自然：

  1. Accept dependencies, don't create them.
  1. 接受相依，不要製造相依。

```typescript // Testable function processOrder(order, paymentGateway) {}

// Hard to test function processOrder(order) { const gateway = new StripeGateway(); } ```

```typescript // Testable function processOrder(order, paymentGateway) {}

// Hard to test function processOrder(order) { const gateway = new StripeGateway(); } ```

  1. Return results, don't produce side effects.
  1. 回傳結果，不要製造副作用。

```typescript // Testable function calculateDiscount(cart): Discount {}

// Hard to test function applyDiscount(cart): void { cart.total -= discount; } ```

```typescript // Testable function calculateDiscount(cart): Discount {}

// Hard to test function applyDiscount(cart): void { cart.total -= discount; } ```

  1. Small surface area. Fewer methods = fewer tests needed. Fewer params = simpler test setup.
  1. 小表面積。 方法更少 = 需要的測試更少。參數更少 = 測試設定更簡單。

Relationships

關係

  • A Module has exactly one Interface (the surface it presents to callers and tests).
  • Depth is a property of a Module, measured against its Interface.
  • A Seam is where a Module's Interface lives.
  • An Adapter sits at a Seam and satisfies the Interface.
  • Depth produces Leverage for callers and Locality for maintainers.
  • 一個模組剛好有一個介面（它呈現在呼叫者與測試面前的表面）。
  • 深度是模組的屬性，相對於它的介面來衡量。
  • 接縫是模組的介面所在之處。
  • 轉接器坐在接縫處並滿足介面。
  • 深度為呼叫者產生槓桿收益、為維護者產生局部性。

Rejected framings

被否決的框架

  • Depth as ratio of implementation-lines to interface-lines (Ousterhout): rewards padding the implementation. We use depth-as-leverage instead.
  • "Interface" as the TypeScript interface keyword or a class's public methods: too narrow — interface here includes every fact a caller must know.
  • "Boundary": overloaded with DDD's bounded context. Say seam or interface.
  • 把深度當成實作行數對介面行數的比率（Ousterhout）：獎勵灌水實作。我們改用深度即槓桿收益。
  • 把「介面」當成 TypeScript 的 interface 關鍵字或類別的公開方法：太窄——這裡的介面包含呼叫者必須知道的每一件事實。
  • 「boundary」：與 DDD 的 bounded context 過載。說seam或interface。

📖 教學解說

codebase-design 的核心概念是深度（Depth）：深模組 = 小介面 + 大量實作。淺模組 = 大介面 + 少許實作。深度的價值是槓桿收益（每單位介面給更多能力）和局部性（變更集中在一個地方）。

四個原則：(1) 深度是介面的屬性，不是實作的屬性。(2) 刪除測試：刪掉模組後，複雜度是消失（=轉送層）還是重現（=在賺住宿費）？(3) 介面就是測試表面——呼叫者和測試跨越同一個接縫。(4) 一個轉接器 = 假設性接縫；兩個 = 真實接縫。

💡 Worked Example

情境：你的 OrderService 有 15 個公開方法，每個都只做一件小事。

  1. 套用深度測試：OrderService 是淺模組——15 個方法的介面幾乎跟實作一樣複雜
  2. 刪除測試：刪掉 OrderService → 複雜度散落在 8 個呼叫者之間 → 它在賺住宿費
  3. 深化方向：把 15 個方法收斂成 3 個——createOrder、fulfillOrder、cancelOrder
  4. 結果：介面從 15 方法縮到 3 方法（小介面），實作把 15 個步驟藏在裡面（大量實作）→ 深模組
  5. 槓桿收益：8 個呼叫者都從 3 個簡單方法受益；局部性：order 邏輯集中在一個地方

⚠️ 常見錯誤

  • 把介面當成 TypeScript interface——這裡的介面是「呼叫者必須知道的每一件事」，不只是型別簽章。
  • 為了測試而抽純函式——如果真正的 bug 藏在「函式如何被呼叫」，抽出來只是轉移問題。
  • 一個轉接器就引入接縫——一個轉接器是假設性的。要有兩個才能確認真的有變異。
  • 把深度當成行數比率——不是「實作行數 / 介面行數」，而是「每單位介面給多少能力」。

✅ 練習 / 驗收清單

  • □ 能區分深模組和淺模組
  • □ 能套用刪除測試判斷模組是否在賺住宿費
  • □ 知道介面 = 呼叫者必須知道的每一件事（不只是型別簽章）
  • □ 知道轉接器的數量決定接縫的真實性
  • □ 能用深度、局部性、槓桿收益來解釋設計決策

🚀 進階真實情境 Worked Example

情境：你接手一個計費系統，發現 BillingClient 有 22 個公開方法，其中 19 個只是把參數轉給底層 HTTP client。你決定用 codebase-design 詞彙做一次深化。

  1. 診斷：22 個方法的介面幾乎跟實作一樣複雜 → 淺模組。套用刪除測試——刪掉 BillingClient，複雜度會散回 9 個呼叫者 → 它在賺住宿費，值得深化。
  2. 分群：22 個方法其實服務三種意圖——訂閱管理、發票、付款事件。三個「想出生的型別」被壓在一個類別裡（Data Clumps 的一種）。
  3. 設計接縫：真正的變化點是底層 API 的供應商（Stripe → Adyen）。現在只有 StripeGateway 一個轉接器 → 假設性接縫，先不拆；等第二家供應商出現再拆。
  4. 深化後介面：subscribe()、bill()、handlePaymentEvent() 三個方法，內部各藏一個小狀態機。介面從 22 → 3，行為藏在裡面。
  5. 驗證：介面就是測試表面——新測試透過三個方法驗證整條計費路徑，不再需要 mock 19 個 HTTP 轉手方法。

設計決策：最容易被忽略的是「先不拆接縫」。工程師常直覺地想「多包一層 adapter 以便未來替換」，但規則是一個轉接器＝假設性接縫——沒有第二個實作出現前，那條接縫只會增加介面面積、降低深度。此例正確的次序是先把行為收進深模組，供應商切換等真實需求出現再拆。

🔬 深入原理擴充

「深度」這個詞取自 John Ousterhout 的 A Philosophy of Software Design，但本技能刻意棄用他的原始定義（實作行數對介面行數的比率），改用「每學習一單位介面所能行使的行為量」。原因：行數比率會被「灌水實作」欺騙——你把 20 行冗餘程式碼塞進模組，比率變深了，但呼叫者沒有獲得任何新能力。深度即槓桿收益，衡量的是介面對呼叫者的價值密度。

對 AI coding assistant 而言，深模組還有第三個好處：可導覽性。agent 讀程式碼時依賴「在對的地方找到對的行為」。淺模組把行為散落在 N 個薄薄的方法裡，agent 必須跳讀全部 N 個才知道整個流程；深模組讓 agent 讀一個介面就能對行為建立模型。improve-codebase-architecture 的「AI-navigability」目標指的就是這個。

陷阱案例：大家常以為「抽成小函式＝好設計」，於是拼命把每個方法拆到 3–5 行、每個小函式一個職責。結果是 200 個彼此呼叫的極小函式，介面面積爆炸，理解一個概念要在 200 個檔案間彈跳。真相是：小而好拆的函式不是目標，深而集中的介面才是。內部可以是任何形狀——甚至一個 60 行的私有函式——只要它不暴露在介面上。用刪除測試判斷，不用「行數多寡」判斷。

🏆 進階挑戰題

  1. 刪除測試實作：你的 FileStore 有 9 個方法（read/write/append/list/delete/rename/copy/move/exists）。跑刪除測試——刪掉後複雜度會在哪裡重現？這告訴你什麼？
  2. 接縫判讀：你的專案用 Postgres，你正考慮抽象一個 Database 介面「以備未來換成 MySQL」。用「一個轉接器 vs 兩個轉接器」原則分析這個決策該不該做。
  3. 介面收斂設計：一個 PaymentProcessor 有 15 個方法，服務三種意圖。把它收斂成 3 個深方法，並說明每個方法隱藏了哪些行為、呼叫者與測試各自獲得什麼。

🏗️ 專案級端到端 Worked Example

專案情境：一個「訂單處理系統」從頭設計，整合 codebase-design 的詞彙貫穿整個專案生命週期——從介面設計、TDD 接縫、架構掃描到重構驗證。

  1. 介面設計：先用 DESIGN-IT-TWICE 平行子代理設計兩種截然不同的訂單介面：(A) 單一 processOrder(order) 深方法（B) 五個步驟方法 validate → charge → fulfill → notify → log。比較深度、局部性、接縫位置 → 選 A。
  2. 接縫落地：把選定的介面放上乾淨接縫，用 /tdd 測試——測試直接跨同一個介面，不 mock 內部。外部相依（付款閘道）用「接受相依」方式注入，不做假設性接縫（目前只有一個 Stripe 轉接器）。
  3. 專案中期：/improve-codebase-architecture 掃描發現 fulfillOrder 的倉儲層有 19 個薄方法（淺模組）→ 用刪除測試確認「刪掉後複雜度散回 9 個呼叫者」→ 深化成 3 個深方法。
  4. 換供應商：需求出現「支援 Adyen」，第二個轉接器出現 → 此刻才拆「付款介面」接縫（兩個轉接器＝真實接縫）。
  5. 驗證：全專案用「介面就是測試表面」原則檢查——所有測試都跨公開介面，沒有任何測試穿透到內部。DOM 與 DB 層的變更不影響測試。

預期輸出：一個介面（processOrder）＋一條接縫（付款）＋一套全跨公開介面的測試。整個專案的呼叫者只知道「怎麼用」，不需要知道「裡面怎麼運作」。

關鍵設計：整個專案只有一個「先拆接縫的決定」——其他接縫都是需求逼出來才拆。這就是「一個轉接器＝假設性接縫」原則在專案規模的體現：介面深度是設計出來的，接縫是真實需求長出來的。

⚙️ 效能 / 品質 / 安全深度

效能：深模組的效能利益在介面面積——呼叫者學一個深方法，比學 19 個薄方法省去大量「理解成本」；對 typecheck 而言，小介面也意味著更少的型別組合面。但注意：深模組內部的大實作仍有自己的複雜度，若內部狀態機寫成 O(n²) 的巢狀迴圈，局部性反而讓效能問題集中在一個地方、更容易被 profiling 找到——這是優點。

品質：品質指標是「可測試性與可導覽性」。可測試性 = 測試全部跨公開介面（介面就是測試表面）；可導覽性 = agent 讀一個介面就能對行為建立模型，不用在 200 個小函式間彈跳。刪除測試是品質的判準：模組刪掉後複雜度重現（在賺住宿費）＝品質好；複雜度消失（轉送層）＝品質差。

安全：小介面 = 小攻擊面。深模組把「驗證、授權、狀態轉換」藏在介面後，呼叫者不可能繞過驗證直接碰到內部資料。風險則在「隱藏的安全行為」——深模組內部的錯誤處理若不透漏給介面（error modes 是介面的一部分），呼叫者可能在不知情下忽略安全失敗。所以介面的定義必須包含 error modes——這正是「介面＝呼叫者必須知道的每一件事」的安全意義。

🏗️ ① 專案級端到端 Worked Example

專案情境：你有一個 2000 行的 OrderService 類別，要拆成深模組。

  1. 先跑 /codebase-design，用詞彙表定義：OrderService 目前是「淺模組」（所有 public method 都暴露內部），目標是「深模組」（只暴露一個 placeOrder() 進入點）。
  2. 用「接縫」概念找出測試點：接縫是 placeOrder() 的公開介面，不是內部的 validate() + calculate() + persist()。
  3. 用「轉接器」把外部依賴（PaymentGateway、InventoryService）從直接呼叫改成注入，讓 OrderService 可以獨立測試。
  4. 用「槓桿收益」評估：拆完後，改一個功能只需要改一個檔案，而不是在 2000 行裡找三個散落的方法。

關鍵：codebase-design 不是「畫架構圖」，而是「決定什麼該藏起來、什麼該露出來」。深模組的核心原則：實作藏在子資料夾中，只能透過進入點檔案觸達。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能深模組的包裝層（adapter）會增加一層間接呼叫。在 hot path 上，這可能是 O(1) 的額外開銷；但在 I/O bound 的場景中，這幾乎可忽略。
品質「深化」的品質指標：模組的 public surface 是否穩定（不常改）、內部實作是否可自由重構（改內部不影響外部）。
安全深模組的「進入點」是天然的安全邊界——所有輸入都經過進入點驗證。確保進入點有 input validation，而不是把驗證留在內部。
