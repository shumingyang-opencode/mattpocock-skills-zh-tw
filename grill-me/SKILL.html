📖 教學解說

grill-me 是 /grilling 原語的無狀態包裝。跟 grill-with-docs 的差別是：grill-me 不寫任何東西到磁碟。它適合在沒有 repo 的地方使用——磨利一個計畫、一個設計、一篇寫作。如果你在工作目錄中，永遠選 grill-with-docs。

Grill 的核心機制：agent 問問題、你做決策。Agent 會鍥而不捨地追問，直到你沒得閃。這是刻意的——模糊的回答只會讓計畫失敗。

💡 Worked Example

情境：你在咖啡店，想磨利一個產品想法，但筆電上沒有 repo。

  1. 呼叫 /grill-me "我想做一個幫工程師寫文件的 CLI 工具"
  2. Agent 問：「目標使用者是誰？個人工程師還是團隊？」→ 你：「個人工程師」
  3. Agent 問：「它跟現有的 docs generator 有什麼不同？」→ 你：「它根據程式碼自動產生文件，不需要手寫」
  4. Agent 問：「支援哪些語言？」→ 你：「先做 TypeScript」
  5. Grill 完後，你有了清晰的想法。回到 repo 後，可以用 grill-with-docs 把這些決策寫進 CONTEXT.md

⚠️ 常見錯誤

  • 在工作目錄中用 grill-me——如果你在有 repo 的地方，永遠選 grill-with-docs。它會留下紙本痕跡。
  • 回答太模糊——Agent 問「你要什麼？」，你回答「你覺得呢？」。Grill 的設計是你做決策。
  • 以為 grill-me 會存檔——grill-me 是無狀態的。session 結束後，對話內容就消失了。

✅ 練習 / 驗收清單

  • □ 知道 grill-me 和 grill-with-docs 的差別
  • □ 只在沒有 repo 的地方使用 grill-me
  • □ 每個問題都有給出具體答案
  • □ Grill 完後有清晰的想法可以帶回 repo

🚀 進階真實情境 Worked Example

情境：你在通勤路上，沒有 repo，想磨利「用 AI 幫同事寫 daily standup 摘要」的工具點子，準備明天跟老闆提案。

  1. 呼叫 /grill-me "我想做一個自動產生 standup 摘要的 CLI 工具"。
  2. Agent 第一輪追問：「它讀什麼來源？」→ 你：「公司 git 的 commit + 我的行事曆」。
  3. Agent 鍥而不捨：「誰是消費者？你自己，還是你老闆？」→ 你：「自己先，老闆後」。
  4. Agent 磨利邊界：「standup 摘要與『commit log 翻譯成人話』的差別是什麼？」→ 你：「摘要要串連成一段敘事，不是條列」——這個回答讓工具的定位瞬間清楚。
  5. Agent 收斂：「先用手動 export 的 JSON 當輸入，不要直接接公司 API，對嗎？」→ 你：「對，第一版避免授權地雷」。
  6. Grill 結束。你帶著「輸入＝commit+行事曆 JSON、輸出＝敘事性摘要、第一版不接 API」三個明確決策去提案。

設計決策：無狀態不代表沒有結構。grill-me 的回合制設計強制你在每個轉折點表態——「誰是消費者」「邊界在哪」「第一版避開什麼」。這些決策若在寫 code 時才想，你已經把第一個錯版交出去了。

🔬 深入原理擴充

grill-me 與 grill-with-docs 共用同一個 /grilling 原語，差別只在「有沒有留下紙本痕跡」。這個設計傳達一個重要原則：思考的過程與思考的產物可以分離。grill-me 優化「把想法想清楚」這一個目標，所以它刻意不寫檔——不寫檔讓 session 更輕、可以在地鐵上開，也不必在乎 repo 是否乾淨。

對 AI coding assistant 而言，grilling 對抗的是模型的順從性偏誤：模型傾向同意使用者、把模糊的目標當成已確定的需求一路做下去。回合制訪談＋「事實是代理的責任、決策是你的責任」的劃分，逼使用者每一次都為決策表態——這就是「減少 agent 自由度」的又一應用。

陷阱案例：很多人把 grill 當成「跟 AI 聊天確認一下」，於是用「你覺得呢？」把問題丟回去。這是 grill 的頭號反模式——把決策推回給代理。代理不懂你的業務、你的限制、你的老闆。如果代理問「第一版支援哪些平台」，你回「你覺得呢？」，得到的答案只是代理的猜測，而且猜完你還會隱隱把它當成自己的承諾。真相是：grill 的輸出品質等於你表態的品質。每一個「你覺得呢」都是一個未做的決策，會在 implement 時以「想當然爾」的姿態復活。

🏆 進階挑戰題

  1. 決策提取：模擬一場三分鐘的 grill 對話，主題「是否該把公司部落格改成 Next.js」。至少提取出五個你必須自己做的決策，並說明為什麼每個決策代理不該替你回答。
  2. 反模式辨識：下列回覆哪些是 grill 的反模式？（a）「你覺得呢」（b）「我沒想過這個，我需要想想」（c）「這不重要吧」（d）「都可以」。逐項說明後果。
  3. 無狀態→有狀態：你在咖啡廳用 grill-me 磨利完點子，回到公司。描述把這些決策「帶進」 grill-with-docs 的完整流程，以及它會寫進哪些檔案。

🏗️ ① 專案級端到端 Worked Example

專案情境：你設計了一個「微服務拆分計畫」，想找人壓力測試。

  1. 先跑 /grill-me，提交你的計畫：「把單體拆成 5 個微服務，用 gRPC 通訊」。
  2. grill-me 會問：「你怎麼決定 5 個服務的邊界？」「gRPC 比 REST 好在哪裡？有什麼代價？」「如果其中一個服務掛了，其他服務怎麼辦？」
  3. 回答後，grill-me 會追问：「你說的『邊界』是用什麼標準定的？DDD 聚合邊界？團隊組織邊界？部署邊界？這三者不一定一樣。」
  4. 經過 3-5 輪質詢，你的計畫會從「我覺得應該拆」變成「我有 3 個具體理由要拆，有 2 個風險要處理，有 1 個替代方案要考虑」。

關鍵：grill-me 的價值不在「打敗你的計畫」，而在「幫你發現你沒想到的假設」。每個「為什麼」都在挖你沒說出口的前提。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能grill-me 的 token 成本與問答輪數成正比。3-5 輪通常是甜蜜點——超過 7 輪通常開始重複。
品質高品質的 grill 需要「具體的假設」。模糊的計畫（「我覺得拆了會比較好」）產出的 grill 也模糊；具體的計畫（「拆分後延遲從 500ms 降到 100ms」）產出的 grill 有深度。
安全Grill-me 不執行任何操作，但它的質詢可能揭露安全假設——例如「你說的認證是用 JWT，但 JWT 的 secret 怎麼管？」。把這些記下來當作安全 checklist。
