resolving-merge-conflicts

照雙方各自的意圖一塊塊解衝突，講清楚原因才動手，絕不按 --abort 擺爛。
  1. See the current state of the merge/rebase. Check git history, and the conflicting files.
  1. 檢視目前狀態，也就是 merge/rebase 的目前狀態。檢查 git 歷史與衝突檔案。
  1. Find the primary sources for each conflict. Understand deeply why each change was made, and what the original intent was. Read the commit messages, check the PRs, check original issues/tickets.
  1. 為每個衝突找出主要來源。深入理解每個變更為什麼被做，以及原始意圖是什麼。讀 commit 訊息、查 PR、查原始 issue/ticket。
  1. Resolve each hunk. Preserve both intents where possible. Where incompatible, pick the one matching the merge's stated goal and note the trade-off. Do not invent new behaviour. Always resolve; never --abort.
  1. 解決每個 hunk。 盡可能保留兩邊的意圖。在不相容之處，選擇符合 merge 陳述目標的一方，並記下取捨。不要發明新行為。永遠解決；絕不 --abort。
  1. Discover the project's automated checks and run them — typically typecheck, then tests, then format. Fix anything the merge broke.
  1. 找出專案的自動化檢查並執行它們——通常是 typecheck，然後測試，然後格式。修好任何被 merge 弄壞的東西。
  1. Finish the merge/rebase. Stage everything and commit. If rebasing, continue the rebase process until all commits are rebased.
  1. 完成 merge/rebase。 把所有東西加入並 commit。如果是在 rebase，繼續 rebase 流程直到所有 commit 都 rebase 完。

📖 教學解說

resolving-merge-conflicts 的核心原則是：追溯到意圖，而不是挑選行。每個衝突都有兩邊的意圖——A 要做 X、B 要做 Y。解決方式不是「選 A 還是選 B」，而是「理解兩邊的意圖，然後找到能保留兩邊意圖的方案」。

關鍵規則：永遠解決，絕不 --abort。Abort 只是把問題推到以後。每一個 hunk 都要解決——如果兩邊不相容，選擇符合 merge 目標的一方，並記下取捨。

💡 Worked Example

情境：你在 rebase main 到你的功能分支，src/export.ts 有衝突。

  1. 看衝突：A 在 export 函數加了 header 驗證、B 改了 CSV 格式
  2. 追溯意圖：A 的 commit 說「fix: prevent empty CSV export」→ 意圖是防止空匯出；B 的 commit 說「feat: support custom CSV delimiter」→ 意圖是加 delimiter 支援
  3. 兩個意圖不衝突——保留 header 驗證 + 保留 delimiter 支援
  4. 手動合併：在 header 驗證之後、CSV 格式化之前加 delimiter 邏輯
  5. 跑自動化檢查：typecheck → tests → format
  6. 完成 rebase

⚠️ 常見錯誤

  • 直接 --abort——把問題推到以後，不是解決它。
  • 隨便選一邊——不追溯意圖就選 A 或 B，可能丟掉另一邊的重要功能。
  • 沒有跑自動化檢查——merge 可能破壞了 typecheck、tests 或 format。衝突解決後一定要跑。
  • 發明新行為——merge 是保留兩邊的意圖，不是趁機加新功能。

✅ 練習 / 驗收清單

  • □ 每個衝突都有追溯到兩邊的意圖（讀 commit 訊息、PR、issue）
  • □ 盡可能保留兩邊的意圖
  • □ 不相容時選擇符合 merge 目標的一方，並記下取捨
  • □ 沒有發明新行為
  • □ 衝突解決後跑過 typecheck → tests → format
  • □ 沒有使用 --abort

🚀 進階真實情境 Worked Example

情境：你在 rebase 功能分支到 main，src/orders.ts 出現衝突。A 邊（你的分支）把「訂單驗證」拆成了獨立模組並改了呼叫點，B 邊（main）把「訂單狀態」從 string 改成 union type。

  1. 看狀態：git status 確認是 rebase 中、衝突集中在 src/orders.ts 與 src/validate.ts。
  2. 找主要來源：A 的 commit 寫「refactor: split order validation」——意圖是驗證邏輯獨立、可重用；B 的 commit 寫「feat: typed order status」——意圖是消滅 magic string。
  3. 逐 hunk 解：驗證模組的型別簽名衝突——A 傳 status: string，B 改成 OrderStatus。兩邊意圖相容：把驗證函式的參數改成 OrderStatus，同時保留 A 的模組拆分。不發明新行為（不順手加驗證規則）。
  4. 跑自動化檢查：typecheck 先爆（幾個呼叫點還用舊 string）→ 依 typecheck 指出的位置逐一修正 → 再跑測試 → 最後跑格式。
  5. 完成 rebase，確認所有 commit 都重放完畢。衝突解決的取捨寫進 commit message（「型別改 union 後，驗證函式同步改用 OrderStatus」）。

設計決策：本例的關鍵是先讀 commit 訊息建立「意圖模型」再動手。若只看 diff 的兩行字面差異，你可能會「選 A 的 string 版本」——那會悄悄把 B 的型別安全改回去，等於在 rebase 中逆向做了一次不該做的 revert。typecheck 在這裡不是「可選的品質檢查」，而是「意圖衝突的偵測器」。

🔬 深入原理擴充

git 的衝突標記（<<<<<<< / ======= / >>>>>>>）呈現的是字面差異，而衝突的真正本質是意圖差異。技能的核心主張是：字面差異只是表面，真正的問題是「兩邊各自的意圖是什麼、它們相容嗎」。這把解決衝突從「挑選行」升級為「設計決策」——先建立兩邊的意圖模型，再合成一個保留雙方意圖的方案。

為什麼「絕不 --abort」？因為 abort 只是把「現在必須解決的衝突」變成「以後某個不知道的時刻的衝突」——同一個檔案、同一對意圖，只是換個時間再撞一次。而且 abort 同時丟掉你已經建立的理解（讀過的 commit、想好的合成方案）。對 AI coding assistant 而言，abort 等於放棄它唯一有價值的資產——上下文。

陷阱案例：很多人以為「衝突越少越好，所以看到衝突就選『看起來比較新』的一邊」。真相是：「新」不代表「正確」——B 邊可能是 hotfix 補丁，A 邊才是長期設計。而且「選一邊」常常悄悄丟掉另一邊的意圖，製造隱形回歸。例如此案例若直接選 A 的 string 版本，main 的型別安全就被靜默撤銷，之後的測試可能全部照跑（因為 string 是 runtime 泛型）——這正是「發明新行為」之外的第二種隱形錯誤：悄悄撤銷意圖。

🏆 進階挑戰題

  1. 意圖合成：A 邊把 getUser(id) 改成回傳 promise，B 邊在同一檔案新增了 getUser` 的快取包裝。寫出兩個意圖各自的內容，以及一個同時保留兩者的合成方案。
  2. 隱形回歸偵測：rebase 後所有測試都綠了，但你懷疑型別安全被靜默撤銷。列出至少三種「測試全綠但意圖被破壞」的可能，並說明各該用哪個檢查抓到。
  3. abort 代價分析：比較「abort 後重做」與「逐 hunk 解決」在（a）時間（b）上下文資產（c）意圖完整性三方面的代價，並說明技能為何把「絕不 abort」寫成硬規則。

🏗️ ① 專案級端到端 Worked Example

專案情境：你和同事同時改了 src/payment/processor.ts，產生了 merge conflict。

  1. 先跑 /resolving-merge-conflicts，它會分析衝突：你改了 processPayment() 的參數型別，同事改了 processPayment() 的 error handling。
  2. 決定取捨策略：型別變更和 error handling 都需要保留——不是「選一邊」，而是「合併兩邊」。
  3. 手動解決衝突：保留你的型別變更 + 同事的 error handling，確保兩者不衝突。
  4. 解決後跑 /tdd 確認 processPayment() 的測試仍然通過——merge conflict 解決後的第一件事是確認「沒有壞掉」。

關鍵：merge conflict 不是「誰贏了」——它是「兩邊的意圖怎麼共存」。解決衝突的目標不是「選一邊」，而是「讓兩邊的意圖都實現」。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能大檔案的 merge conflict（200+ 行衝突）解決時間隨衝突行數線性成長。建議先用 git diff --name-only 篩出衝突檔案，逐一解決。
品質解決衝突後的第一件事是跑測試——衝突解決可能引入邏輯錯誤（例如合併時丟失了某個 if 分支）。確保 /tdd 是解決衝突後的必跑步驟。
安全合併時可能意外引入對方的 credential 或 API key——確保 git diff 中沒有不該出現的 secret。用 git diff --check 可以自動偵測。
