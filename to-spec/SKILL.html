to-spec

把聊完的共識整理成一份規格丟進 tracker，不用再訪談一遍。

This skill takes the current conversation context and codebase understanding and produces a spec. Do NOT interview the user — just synthesize what you already know.

這個技能取用目前對話的上下文與程式碼庫理解，產出一份規格說明。不要訪談使用者——只要綜合你已經知道的內容。

The issue tracker and triage label vocabulary should have been provided to you — run /setup-matt-pocock-skills if not.

Issue 追蹤器與分診標籤詞彙應該已經提供給你——如果沒有，執行 /setup-matt-pocock-skills。

Process

流程

  1. Explore the repo to understand the current state of the codebase, if you haven't already. Use the project's domain glossary vocabulary throughout the spec, and respect any ADRs in the area you're touching.
  1. 探索 repo 以了解程式碼庫目前的狀態，如果你還沒做的話。在整份規格說明中，使用專案的領域詞彙表詞彙，並尊重你接觸區域的任何 ADR。
  1. Sketch out the seams at which you're going to test the feature. Existing seams should be preferred to new ones. Use the highest seam possible. If new seams are needed, propose them at the highest point you can. The fewer seams across the codebase, the better - the ideal number is one.
  1. 勾勒出你將測試該功能的接縫。既有接縫應優先於新接縫。使用盡可能最高的接縫。如果需要新接縫，在你能達到的最高點提出它們。整個程式碼庫的接縫越少越好——理想數量是一個。

Check with the user that these seams match their expectations.

與使用者確認這些接縫符合他們的期望。

  1. Write the spec using the template below, then publish it to the project issue tracker. Apply the ready-for-agent triage label - no need for additional triage.
  1. 使用下方範本撰寫規格說明，然後發佈到專案 Issue 追蹤器。套用 ready-for-agent 分診標籤——不需要額外的分診。

Problem Statement

The problem that the user is facing, from the user's perspective.

Solution

The solution to the problem, from the user's perspective.

User Stories

A LONG, numbered list of user stories. Each user story should be in the format of:

  1. As an , I want a , so that

1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending

This list of user stories should be extremely extensive and cover all aspects of the feature.

Implementation Decisions

A list of implementation decisions that were made. This can include:

  • The modules that will be built/modified
  • The interfaces of those modules that will be modified
  • Technical clarifications from the developer
  • Architectural decisions
  • Schema changes
  • API contracts
  • Specific interactions

Do NOT include specific file paths or code snippets. They may end up being outdated very quickly.

Exception: if a prototype produced a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape), inline it within the relevant decision and note briefly that it came from a prototype. Trim to the decision-rich parts — not a working demo, just the important bits.

Testing Decisions

A list of testing decisions that were made. Include:

  • A description of what makes a good test (only test external behavior, not implementation details)
  • Which modules will be tested
  • Prior art for the tests (i.e. similar types of tests in the codebase)

Out of Scope

A description of the things that are out of scope for this spec.

Further Notes

Any further notes about the feature.

問題陳述

使用者正面臨的問題，從使用者的視角出發。

解決方案

問題的解決方案，從使用者的視角出發。

使用者故事

一份很長、編號的使用者故事清單。每個使用者故事的格式應為：

  1. 作為 ，我想要 ，以便

1. 作為行動銀行客戶，我想要查看帳戶餘額，以便對我的支出做出更明智的決策

這份使用者故事清單應該極其詳盡，涵蓋功能的各個面向。

實作決策

已作實作決策的清單。可以包含：

  • 將被建置／修改的模組
  • 那些將被修改的模組的介面
  • 來自開發者的技術釐清
  • 架構決策
  • Schema 變更
  • API 合約
  • 特定的互動

不要包含具體的檔案路徑或程式碼片段。它們很可能很快就過時。

例外：如果原型產出了一個比散文更能精確編碼決策的片段（狀態機、reducer、schema、型別形狀），就把它內嵌在相關決策中，並簡短註明它來自原型。只保留富含決策的部分——不是可運作的示範，只是重要的片段。

測試決策

已作測試決策的清單。包含：

  • 說明什麼構成好的測試（只測試外部行為，不測試實作細節）
  • 哪些模組將被測試
  • 測試的既有先例（也就是程式碼庫中類似型別的測試）

超出範圍

這份規格說明超出範圍之事的描述。

補充說明

關於此功能的任何補充說明。

📖 教學解說

to-spec 的工作是把 grill 產出的散裝決策，收斂成一份結構化的規格說明。規格的目的是讓 implement 有明確的方向——它不需要包含所有實作細節，但必須回答「要建什麼、為什麼、怎麼驗收」。

規格模板有四個核心區塊：問題陳述（從使用者視角）、解決方案（從使用者視角）、使用者故事（極其詳盡）、實作決策（不包含具體檔案路徑）。最後一個是關鍵——具體路徑很快就過時，規格應該描述決策而不是實作。

💡 Worked Example

從 grill 到 spec 的轉換：

  1. Grill 的 CONTEXT.md 裡有：「支援日期範圍篩選」「先只做 CSV」「匯出到下載串流」
  2. to-spec 把這些決策重新組織成規格模板：
    • 問題陳述：「管理員需要匯出用戶資料到 CSV，但目前沒有匯出功能」
    • 使用者故事：「作為管理員，我想要匯出指定日期範圍的用戶資料，以便做離線分析」
    • 實作決策：「使用 CSV 串流（不一次載入全部資料到記憶體）」「篩選條件從 query string 讀取」
  3. 規格不會寫「在 src/export.ts 裡建 exportCSV 函數」——那是 implement 的事

⚠️ 常見錯誤

  • 規格包含具體檔案路徑或程式碼片段——它們很快就過時。例外：如果 prototype 產出的片段比散文更能精確編碼決策（狀態機、reducer、schema），可以內嵌但要註明來源。
  • 使用者故事不夠詳盡——規格模板要求「極其詳盡」。每一個 edge case 都該在使用者故事中被覆蓋。
  • 把規格當成實作指南——規格描述「要做什麼」，不是「怎麼做」。具體的實作方式由 implement 決定。
  • 沒有包含 Out of Scope——明確列出什麼不在範圍內，能防止 implement 做多做少。

✅ 練習 / 驗收清單

  • □ 規格包含四個核心區塊（問題陳述、解決方案、使用者故事、實作決策）
  • □ 使用者故事極其詳盡，覆蓋所有 edge case
  • □ 沒有具體檔案路徑或程式碼片段（除非來自 prototype 且有標註）
  • □ 有明確的 Out of Scope 區塊
  • □ 有 Testing Decisions 區塊（描述什麼是好測試、哪些模組要測）

🚀 進階真實情境 Worked Example

情境：你跟設計師 grill 完了「購物車結帳流程改版」，CONTEXT.md 裡有十幾個決策，包括「結帳改單頁」「支援 guest checkout」「付款失敗留在原頁」。現在要收斂成 spec。

  1. 探索 repo：確認既有結帳模組的狀態，用 CONTEXT.md 詞彙（checkout、guest checkout、payment failure）貫穿整份 spec。
  2. 勾勒測試接縫：既有最高接縫是 POST /api/checkout endpoint。spec 決定沿用（既有接縫優先、用最高的接縫、全 repo 接縫數量維持最少）。與使用者確認。
  3. 寫 spec：問題陳述（從使用者的視角）、解決方案、使用者故事（逐條覆蓋：訪客結帳、會員結帳、付款失敗重試、單頁轉場）、實作決策（結帳改單頁、guest checkout 引入、付款失敗留在原頁）、測試決策（只測外部行為、測 /api/checkout、prior art 是既有 checkout 測試）。
  4. 實作決策不寫檔案路徑或程式碼——只寫「引入 guest checkout 身分」這種決策層級描述。
  5. Out of Scope：寫明「不包含新付款方式（如 line pay）、不包含結帳頁重新設計（設計師之後單獨開）」。
  6. 發佈到 issue tracker，套 ready-for-agent 標籤——不需要再分診。

設計決策：本例的關鍵是「付款失敗留在原頁」這種從使用者視角描述的決策——spec 不該寫「把 error 物件 return 給前端」，而該寫使用者會經歷的行為。這樣 implement 才能自己決定技術做法，而驗收時能用使用者行為判斷是否完成。

🔬 深入原理擴充

to-spec 的「不訪談、只綜合」是刻意與 grill 對立的設計。grill 是發散（問很多問題、產出很多決策），spec 是收斂（把決策組織成可交付的結構）。若 to-spec 也開始訪談，就會把「已討論過的事」再問一遍，浪費 context 且打斷流程。這背後是「決策只做一次」原則：grill 已做的決策，spec 直接採用，不再重開。

「實作決策不寫具體路徑／程式碼」是對過時風險的管理：檔案路徑與程式碼片段的生命週期以天計，spec 的生命週期以週計。寫進去，規格發佈三天後就開始撒謊。例外只有一種——prototype 產出「比散文更能精確編碼決策」的片段（狀態機、schema、型別形狀），這種片段內嵌的是決策本身而非實作細節，可以留下。

陷阱案例：很多人以為「規格越詳細越好」，於是在 Implementation Decisions 裡寫下「在 src/checkout.ts 建立 CheckoutService，用 repository pattern，注入 PaymentGateway」。真相是：規格描述「要做什麼」，不是「怎麼做」。repo pattern 或 service 結構是實作選擇，寫進規格等於在還沒看見程式碼前就承諾了架構——這正是 to-tickets 的「把規格當成實作指南」反模式，也是 codebase-design 警告的「過早收斂」。

🏆 進階挑戰題

  1. 決策分級：把以下十個句子分成「該進規格」與「該留給 implement」兩組：（a）用 Postgres（b）在 src/checkout.ts 建檔（c）結帳改單頁（d）用 repository pattern（e）付款失敗留在原頁（f）支援 guest checkout（g）注入 PaymentGateway（h）引入 guest 身分模型（i）前端用 React Query（j）不包含新付款方式。並說明分組依據。
  2. 接縫數量：spec 指出測試接縫該「越少越好，理想是一個」。若你的功能跨 API＋背景任務，設計一個單一最高接縫能涵蓋的情境，並說明為什麼這比兩個接縫好。
  3. prototype 片段內嵌：prototype 產出一個 15 行的狀態機定義，精確編碼「付款失敗→留在原頁→重試」的行為。寫出該怎麼把它內嵌進 spec 的實作決策（含註明來源與修剪原則）。

🏗️ ① 專案級端到端 Worked Example

專案情境：你和團隊討論了 30 分鐘「使用者驗證流程」，有共識但沒有文件。

  1. 先跑 /to-spec，它會從對話記錄中提煉出規格：驗證方式（email + password）、token 策略（JWT, 7 天過期）、錯誤處理（401/403/429）。
  2. 規格會自動包含 acceptance criteria：「使用者可以用 email + password 登入」「token 過期後自動 redirect 到登入頁」「5 次錯誤後鎖定 15 分鐘」。
  3. 把規格發佈到 issue tracker：每條 acceptance criteria 對應一張 ticket。
  4. 規格可以被 /implement 直接使用——implement 會逐條讀 acceptance criteria 並實作。

關鍵：to-spec 的價值在「把口頭共識變成可執行的規格」。不需要額外訪談——它只綜合你已經討論過的內容。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能to-spec 的 token 成本與對話長度成正比。30 分鐘的對話大約是 3-5K tokens——在預算內。如果對話超過 1 小時，先用 /handoff 壓縮再跑 to-spec。
品質規格的品質取決於「對話是否有足夠的細節」。如果對話只說「做一個登入功能」，規格會很粗糙；如果對話說了「用 JWT、7 天過期、5 次鎖定」，規格會很具體。
安全規格中可能包含安全相關的決策（例如「JWT 的 secret 用 HMAC-SHA256」）——確保這些決策被記錄在 ADR 中，而不只是在規格裡一行帶過。
