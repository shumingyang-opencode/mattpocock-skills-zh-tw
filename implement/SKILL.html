📖 教學解說

implement 是主流程的執行引擎。它本身很薄——只有五條規則——因為真正的重活交給了它內部驅動的 /tdd 和收尾的 /code-review。這種「薄外包裝 + 原語組合」的設計，正是 write-great-skills 提倡的 pattern：SKILL.md 保持小，把行為委派給已經存在的原語。

關鍵設計決策：implement 先跑 typecheck，再跑單一測試，最後跑完整套件。這是為了保持快速回饋迴圈——紅-綠循環不該被完整的測試套件拖慢。commit 發生在 code-review 通過之後，確保進版的都是審查過的。

💡 Worked Example

情境：你有一張 ticket：「實作 /api/export CSV 端點」，已經有了 to-spec 產出的規格。

  1. 讀取規格，確認接縫：公開介面是 POST /api/export，回傳 CSV 檔案串流
  2. 呼叫 /tdd：先寫一支測試——「給定有效的 JSON body，回傳 Content-Type: text/csv」→ 紅
  3. 寫最小實作讓測試變綠：只實作 CSV 串流，不做 authentication、不做 rate limiting
  4. 確認型別檢查通過（npx tsc --noEmit）
  5. 重複步驟 2–4，逐步加入邊緣案例（空 body、欄位名包含逗號等）
  6. 最後跑完整測試套件確認沒有回歸
  7. 呼叫 /code-review，確認通過後 commit

⚠️ 常見錯誤

  • 在 implement 裡自己寫所有實作——implement 的本質是「驅動 tdd」，不是自己寫一大坨程式碼。每一個切片都該走紅-綠循環。
  • 跳過 typecheck 直接跑測試——typecheck 是最快能抓到介面錯誤的檢查。先跑它能避免在紅-綠循環中浪費時間在型別錯誤上。
  • 在最後才跑完整測試套件——每個切片完成後都該跑一次，確保沒有回歸。等到最後才跑，回歸範圍已經很大了。
  • commit 前不跑 code-review——implement 的收尾條件就是 code-review 通過。沒有審查就 commit = 把品質保障從流程中移除。

✅ 練習 / 驗收清單

  • □ 能說明 implement 的內部流程（tdd → typecheck → code-review → commit）
  • □ 知道 pre-agreed seams 的意思（事先與使用者確認要測哪些接縫）
  • □ 每個實作切片都走了紅-綠循環
  • □ typecheck 在每個切片後都有跑
  • □ 完整測試套件在最後有跑
  • □ code-review 在 commit 前有跑

🚀 進階真實情境 Worked Example

情境：你拿到一張 ticket：「在結帳流程中整合第三方折扣碼服務」，spec 指定的接縫是 applyDiscount(code, cart)，回傳打折後的 cart 與驗證訊息。

  1. 確認接縫：spec 說測試接縫是公開函式 applyDiscount，且既有測試已存在同一個檔案（prior art）。與使用者確認後開始。
  2. 垂直切片 1：it('對有效折扣碼回傳打折 cart') → 紅。建立最小實作：呼叫折扣服務的 validate(code)，通過則套用折扣 → 綠。
  3. 每個切片後跑 typecheck（npx tsc --noEmit），再跑該測試檔，不跑全量。
  4. 垂直切片 2：it('對過期折扣碼回傳錯誤訊息') → 紅。在 validate 失敗分支回傳錯誤物件 → 綠。
  5. 垂直切片 3：it('折扣碼同時適用多商品') → 紅。修複製邏輯讓折扣按比例分配到各商品 → 綠。
  6. 最後跑完整測試套件確認無回歸 → /code-review 雙軸審查 → 通過後 commit。

設計決策：本例刻意讓折扣服務是外部相依。實作時先確認測試接縫接受相依注入（applyDiscount(code, cart, discountService)），而不是在函式內部 new DiscountClient()——這是 codebase-design「接受相依，不要製造相依」在 TDD 接縫上的落地。型別與測試都寫在公開接縫上，重構內部時測試不會壞。

🔬 深入原理擴充

implement 的「薄」是刻意的：五條規則裡沒有「怎麼寫程式碼」，因為那是 /tdd 的工作。這是一個委派型技能——它不重複造輪子，而是以正確的次序呼叫既有原語（tdd → typecheck → 全量測試 → code-review → commit）。這種設計讓每個 skill 只保有一個真相來源，也讓「implement 該怎麼做」不會與「tdd 該怎麼做」分叉。

規則的次序本身傳達了成本結構：typecheck 每切片都跑、單一測試檔每切片都跑、完整套件只在最後跑一次。這是把回饋迴圈調到最緊的工程決策——紅-綠循環的核心是「快」，全量套件會拖慢它，所以只在收尾時跑，此時它的角色從「指引」變成「驗證」。

陷阱案例：很多人以為「implement = 把整個功能一口氣寫完，最後再跑測試」。這正是 tdd 明令禁止的水平切片——先寫全部實作，再寫全部測試，測試驗證的是「想像中的行為」而非「逐步長出的行為」。更糟的是，一口氣寫完後若有 40 個測試失敗，你無從分辨「哪個失敗對應哪個決策錯誤」。真相是：implement 的品質是「逐步可見」的——每個切片從紅到綠的過程本身就是證據，證明這段實作是被測試逼出來的，而不是事後補測驗證的。

🏆 進階挑戰題

  1. 接縫確認：spec 給的測試接縫是「公開函式」，但你發現真正複雜的邏輯藏在內部。用 codebase-design 詞彙說明你該怎麼做，以及為什麼不該為了測試方便把內部函式公開。
  2. 切片次序：一個「匯出 CSV 並寄 email」的功能。排出三個垂直切片的次序（每片要端對端可用），並標出每片的紅-綠測試長什麼樣。
  3. 回饋調校：你的完整測試套件要 8 分鐘。說明在紅-綠循環中、切片結束時、收尾時三個時點各該跑什麼，以及這樣安排的依據。
