namecode-review
description (EN)Review the changes since a fixed point (commit, branch, tag, or merge-base) along two axes — Standards (does the code follow this repo's documented coding standards?) and Spec (does the code match what the originating issue/spec asked for?). Runs both reviews in parallel sub-agents and reports them side by side. Use when the user wants to review a branch, a PR, work-in-progress changes, or asks to "review since X".
說明 (繁中)沿兩軸審查自某個固定點（commit、分支、標籤或合併基點）以來的變更——規範（軸）（程式碼是否符合此 repo 記錄的編碼規範？）與規格（軸）（程式碼是否符合原始 issue/規格的要求？）。以平行子代理執行兩種審查並排呈現。當使用者想審查分支、PR、進行中的變更，或說「review since X」時使用。

code-review

雙軸檢查：有沒有照團隊規範、有沒有照規格做出來。

Two-axis review of the diff between HEAD and a fixed point the user supplies:

對 HEAD 與使用者提供的固定點之間的 diff 做雙軸審查：

  • Standards — does the code conform to this repo's documented coding standards?
  • Spec — does the code faithfully implement the originating issue / spec?
  • 規範（軸）——程式碼是否符合此 repo 記錄的編碼規範？
  • 規格（軸）——程式碼是否忠實實作原始 issue / 規格？

Both axes run as parallel sub-agents so they don't pollute each other's context, then this skill aggregates their findings.

兩個軸都以平行子代理執行，讓它們不污染彼此的上下文，然後本技能匯總它們的發現。

The issue tracker should have been provided to you — run /setup-matt-pocock-skills if docs/agents/issue-tracker.md is missing.

Issue 追蹤器應該已經提供給你——如果 docs/agents/issue-tracker.md 缺失，執行 /setup-matt-pocock-skills。

Process

流程

1. Pin the fixed point

1. 釘住固定點

Whatever the user said is the fixed point — a commit SHA, branch name, tag, main, HEAD~5, etc. If they didn't specify one, ask for it.

無論使用者說的固定點是什麼——一個 commit SHA、分支名稱、標籤、main、HEAD~5 等。如果他們沒指定，就問。

Capture the diff command once: git diff <fixed-point>...HEAD (three-dot, so the comparison is against the merge-base). Also note the list of commits via git log <fixed-point>..HEAD --oneline.

把 diff 指令記下來一次：git diff <fixed-point>...HEAD（三點，這樣比較對象是合併基點）。也要用 git log <fixed-point>..HEAD --oneline 記下 commit 清單。

Before going further, confirm the fixed point resolves (git rev-parse <fixed-point>) and the diff is non-empty. A bad ref or empty diff should fail here — not inside two parallel sub-agents.

進一步之前，確認固定點能解析（git rev-parse <fixed-point>）而且 diff 非空。壞的 ref 或空的 diff 應該在這裡失敗——而不是在兩個平行子代理內部。

2. Identify the spec source

2. 找出規格來源

Look for the originating spec, in this order:

依此順序尋找原始規格：

  1. Issue references in the commit messages (#123, Closes #45, GitLab !67, etc.) — fetch via the workflow in docs/agents/issue-tracker.md.
  2. A path the user passed as an argument.
  3. A spec file under docs/, specs/, or .scratch/ matching the branch name or feature.
  4. If nothing is found, ask the user where the spec is. If they say there isn't one, the Spec sub-agent will skip and report "no spec available".
  1. commit 訊息中的 issue 引用（#123、Closes #45、GitLab !67 等）——透過 docs/agents/issue-tracker.md 中的工作流程擷取。
  2. 使用者以參數傳入的路徑。
  3. docs/、specs/ 或 .scratch/ 下符合分支名稱或功能的規格檔。
  4. 如果什麼都沒找到，問使用者規格在哪。如果他們說沒有，規格子代理會跳過並回報「no spec available」。

3. Identify the standards sources

3. 找出規範來源

Anything in the repo that documents how code should be written, such as CODING_STANDARDS.md or CONTRIBUTING.md.

repo 中任何記錄程式碼應如何撰寫的東西，例如 CODING_STANDARDS.md 或 CONTRIBUTING.md。

On top of whatever the repo documents, the Standards axis always carries the smell baseline below — a fixed set of Fowler code smells (Refactoring, ch.3) that applies even when a repo documents nothing. Two rules bind it:

在 repo 記錄的任何東西之上，規範軸永遠攜帶下面這份壞味道基線——一組固定的 Fowler 壞味道（Refactoring，第 3 章），即使 repo 什麼都沒記錄也適用。兩條規則綁定它：

  • The repo overrides. A documented repo standard always wins; where it endorses something the baseline would flag, suppress the smell.
  • Always a judgement call. Each smell is a labelled heuristic ("possible Feature Envy"), never a hard violation — and, like any standard here, skip anything tooling already enforces.
  • repo 優先。 記錄在案的 repo 標準永遠勝出；當它背書基線會標記的某個東西時，抑制該壞味道。
  • 永遠是判斷。 每個壞味道都是帶標籤的啟發式（「可能是 Feature Envy」），從來不是硬性違規——而且像這裡的任何標準一樣，跳過任何工具已經強制的東西。

Each smell reads what it is → how to fix; match it against the diff:

每個壞味道讀成它是什麼 → 如何修；把它對上 diff：

  • Mysterious Name — a function, variable, or type whose name doesn't reveal what it does or holds. → rename it; if no honest name comes, the design's murky.
  • Duplicated Code — the same logic shape appears in more than one hunk or file in the change. → extract the shared shape, call it from both.
  • Feature Envy — a method that reaches into another object's data more than its own. → move the method onto the data it envies.
  • Data Clumps — the same few fields or params keep travelling together (a type wanting to be born). → bundle them into one type, pass that.
  • Primitive Obsession — a primitive or string standing in for a domain concept that deserves its own type. → give the concept its own small type.
  • Repeated Switches — the same switch/if-cascade on the same type recurs across the change. → replace with polymorphism, or one map both sites share.
  • Shotgun Surgery — one logical change forces scattered edits across many files in the diff. → gather what changes together into one module.
  • Divergent Change — one file or module is edited for several unrelated reasons. → split so each module changes for one reason.
  • Speculative Generality — abstraction, parameters, or hooks added for needs the spec doesn't have. → delete it; inline back until a real need shows.
  • Message Chains — long a.b().c().d() navigation the caller shouldn't depend on. → hide the walk behind one method on the first object.
  • Middle Man — a class or function that mostly just delegates onward. → cut it, call the real target direct.
  • Refused Bequest — a subclass or implementer that ignores or overrides most of what it inherits. → drop the inheritance, use composition.
  • 神祕名稱（Mysterious Name）——函式、變數或型別的名字看不出它做什麼或存什麼。→ 重新命名；如果想不出誠實的名字，設計很模糊。
  • 重複程式碼（Duplicated Code）——相同的邏輯形狀在變更中出現於多個 hunk 或檔案。→ 抽取共享形狀，兩邊都呼叫它。
  • 特徵依附（Feature Envy）——方法觸及另一個物件的資料比自己的多。→ 把方法移到它所羨慕的資料上。
  • 資料叢集（Data Clumps）——相同的幾個欄位或參數一直結伴同行（一個想出生的型別）。→ 把它們捆成一個型別，傳那個。
  • 基本型別執著（Primitive Obsession）——用基本型別或字串代替某個值得擁有自己型別的領域概念。→ 給那個概念一個自己的小型別。
  • 重複 switch（Repeated Switches）——同一型別上相同的 switch / if 級聯在變更中重複出現。→ 用多型取代，或一個兩處共享的 map。
  • 散彈槍手術（Shotgun Surgery）——一個邏輯變更迫使 diff 中許多檔案被散落編輯。→ 把一起變更的東西收攏到一個模組。
  • 發散式變更（Divergent Change）——一個檔案或模組因幾個無關的理由被編輯。→ 拆分，讓每個模組只為一個理由變更。
  • 投機性一般化（Speculative Generality）——為規格沒有的需求加入的抽象、參數或鉤子。→ 刪掉它；在真實需求出現前內嵌回去。
  • 訊息鏈（Message Chains）——長 a.b().c().d() 導覽，呼叫者不該依賴它。→ 把這趟走訪藏到第一個物件上的單一方法後面。
  • 中間人（Middle Man）——類別或函式多半只是轉手往下委派。→ 砍掉它，直接呼叫真正的目標。
  • 拒絕遺贈（Refused Bequest）——子類別或實作者忽略或覆寫它繼承的大部分東西。→ 放棄繼承，改用組合。

4. Spawn both sub-agents in parallel

4. 平行啟動兩個子代理

Send a single message with two Agent tool calls. Use the general-purpose subagent for both.

發送單一訊息、兩個 Agent 工具呼叫。兩者都用 general-purpose 子代理。

Standards sub-agent prompt — include:

規範子代理提示——包含：

  • The full diff command and commit list.
  • The list of standards-source files you found in step 3, plus the smell baseline from step 3 pasted in full — the sub-agent has no other access to it.
  • The brief: "Report — per file/hunk where relevant — (a) every place the diff violates a documented standard: cite the standard (file + the rule); and (b) any baseline smell you spot: name it and quote the hunk. Distinguish hard violations from judgement calls — documented-standard breaches can be hard, but baseline smells are always judgement calls, and a documented repo standard overrides the baseline. Skip anything tooling enforces. Under 400 words."
  • 完整的 diff 指令與 commit 清單。
  • 你在第 3 步找到的規範來源檔案清單，加上第 3 步的壞味道基線完整貼上——子代理沒有其他途徑取得它。
  • 簡報：「回報——在相關處逐檔案 / hunk——(a) diff 違反記錄在案標準的每一處：引用標準（檔案 + 規則）；以及 (b) 你注意到的任何基線壞味道：指出名字並引用 hunk。區分硬性違規與判斷——記錄在案的標準違規可以是硬性的，但基線壞味道永遠是判斷，而且記錄在案的 repo 標準覆蓋基線。跳過任何工具已強制的東西。400 字以內。」

Spec sub-agent prompt — include:

規格子代理提示——包含：

  • The diff command and commit list.
  • The path or fetched contents of the spec.
  • The brief: "Report: (a) requirements the spec asked for that are missing or partial; (b) behaviour in the diff that wasn't asked for (scope creep); (c) requirements that look implemented but where the implementation looks wrong. Quote the spec line for each finding. Under 400 words."
  • diff 指令與 commit 清單。
  • 規格的路徑或擷取的內容。
  • 簡報：「回報：(a) 規格要求但缺失或部分實作的需求；(b) diff 中沒有被要求卻存在的行為（範圍蔓延）；(c) 看起來已實作但實作看起來錯誤的需求。每個發現引用規格的原文。400 字以內。」

If the spec is missing, skip the Spec sub-agent and note this in the final report.

如果規格缺失，跳過規格子代理並在最終報告中註明。

5. Aggregate

5. 匯總

Present the two reports under ## Standards and ## Spec headings, verbatim or lightly cleaned. Do not merge or rerank findings — the two axes are deliberately separate (see Why two axes).

在 ## Standards 與 ## Spec 標題下呈現兩份報告，原樣或輕度清理。不要合併或重新排序發現——兩個軸刻意分開（見《為什麼兩軸》）。

End with a one-line summary: total findings per axis, and the worst issue within each axis (if any). Don't pick a single winner across axes — that's the reranking the separation exists to prevent.

以一行摘要結尾：每個軸的發現總數，以及每個軸內最嚴重的問題（如果有的話）。不要跨軸選一個總冠軍——那正是分離所要防止的重新排序。

Why two axes

為什麼兩軸

A change can pass one axis and fail the other:

一個變更可以過一軸而掛另一軸：

  • Code that follows every standard but implements the wrong thing → Standards pass, Spec fail.
  • Code that does exactly what the issue asked but breaks the project's conventions → Spec pass, Standards fail.
  • 遵循所有標準但實作錯誤的東西 → 規範過、規格掛。
  • 確切做了 issue 要求但破壞專案慣例的程式碼 → 規格過、規範掛。

Reporting them separately stops one axis from masking the other.

分開回報能阻止一個軸掩蓋另一個。

📖 教學解說

code-review 的核心設計是雙軸分離：規範（Standards）和規格（Spec）由平行子代理分別審查，避免一個軸的發現掩蓋另一個。為什麼要分開？因為一個變更可以過規範但錯方向（寫得很好但做錯事），也可以做對事但破壞慣例（做對了但寫得很醜）。

規範軸永遠攜帶 smell baseline——一組 Fowler 壞味道，即使 repo 什麼都沒記錄也適用。這是一個「不管有沒有文件都該檢查」的最低標準。規格軸的關鍵問題是「規格從哪來」——它按優先順序搜尋：commit message 裡的 issue 引用 → 使用者提供的路徑 → docs/specs 裡的規格檔 → 問使用者。

💡 Worked Example

情境：你完成了一個功能分支，要 review git diff main...HEAD。

  1. 釘住固定點：git diff main...HEAD（三點，比對合併基點）。確認 diff 非空。
  2. 找規格來源：commit message 裡有 Closes #42，從 issue tracker 拉 #42 的內容。
  3. 規範子代理檢查：是否有 god function？是否有 magic number？是否遵循專案的 naming convention？
  4. 規格子代理檢查：#42 要求的功能是否完整實現？有沒有遺漏 edge case？
  5. 兩軸結果並排呈現。如果規範過但規格掛，你知道方向錯了；如果規格過但規範掛，你知道需要重構。

⚠️ 常見錯誤

  • 跨軸選「最嚴重」問題——code-review 明確禁止跨軸比較。兩軸分開回報，因為它們衡量的是不同東西。
  • 忘記固定點——「review 一下」但沒指定從哪裡開始。固定點必須明確：commit SHA、branch name、tag。
  • 在空 diff 上啟動子代理——先確認 diff 非空。空 diff 應該在啟動平行子代理之前就失敗。
  • 忽略 smell baseline——即使 repo 沒有 CODING_STANDARDS.md，規範軸仍會檢查 Fowler 壞味道。這是最低標準。

✅ 練習 / 驗收清單

  • □ 能說明雙軸分離的設計理由（避免掩蓋效應）
  • □ 知道規格來源的搜尋優先順序
  • □ 知道 smell baseline 是什麼（Fowler 壞味道，repo 無文件也適用）
  • □ 每次 review 都有明確的固定點
  • □ 兩軸結果是分開回報，沒有跨軸比較

🚀 進階真實情境 Worked Example

情境：你接手一個團隊的 PR，內容是把驗證邏輯從 controller 移到一個新的 validateOrder 模組。你已經知道固定點是 main，規格來源是 ticket #204。

  1. 釘住固定點：git diff main...HEAD（三點）。git rev-parse main 解析成功、diff 非空。
  2. 找規格：commit message 寫 Closes #204，從 issue tracker 拉出 #204——「把驗證邏輯集中到單一模組，讓訂單 API 只處理路由」。
  3. 規範子代理：檢查 diff 是否符合 CODING_STANDARDS.md。發現 validateOrder 用 any 收參數，違反 repo 的「禁止隱式 any」規則（硬性違規）。
  4. 規格子代理：對照 #204——規格要求「驗證邏輯集中」，但 diff 仍把 email 格式驗證留在 controller（範圍不足），同時新增了 #204 沒要求的 validateDiscount（範圍蔓延）。
  5. 並排呈現兩軸結果：規範軸抓到隱式 any；規格軸抓到範圍不足與蔓延。開發者依序修正，再次 review 直到兩軸都過。

設計決策：這次審查最關鍵的決定是不要把「移驗證」與「順手加 validateDiscount」混為一談。規格軸的設計就是為了攔這種「沒被要求的行為」——如果只跑規範軸，範圍蔓延會完全通過。雙軸分離在此刻證明價值。

🔬 深入原理擴充

雙軸審查在認知上對應到兩個獨立的評估維度：規範軸回答「這寫得好不好」，規格軸回答「這做對不對」。心理學上兩者會互相污染——一個「做對了但寫得醜」的 diff，若合併評估，審查者常因整體觀感好而放過規格瑕疵。分離子代理正是阻斷這種錨定效應的工程手法。

對 AI coding assistant 而言，git diff 是它理解變更的唯一窗口。因此審查品質上限取決於 diff 是否包含足夠上下文。實務上常見問題是 diff 太大（整包 2000 行）或太小（忽略已改未加的檔案），讓子代理在殘缺輸入上做判斷。

陷阱案例：很多人以為「三點 diff 一定比兩點好」——其實兩者語義不同。`git diff main...HEAD` 比對的是 merge-base 與 HEAD（只看你的分支真正引入的變更），`git diff main..HEAD` 比對的是 main 目前狀態與 HEAD（會混入 main 上新增的內容）。若誤用兩點，review 會把同事的變更當成你的範圍，兩個軸都會誤報。審查前務必確認固定點語義。

🩺 診斷式疑難排解表

症狀可能原因解決方案
固定點解析失敗（bad ref）使用者給了不存在的 commit / 分支名，或打錯字用 git rev-parse 驗證；失敗就回問使用者正確的 ref，不要在子代理內才爆錯
diff 是空的但使用者說有變更固定點設在 HEAD 自己，或分支還沒 commit確認固定點早於目前 HEAD；未 commit 的變更改用 git diff（無參數）
規格軸找不到任何規格commit 沒有 issue 引用、docs/ 下也沒有規格檔依優先序搜尋後問使用者；真的沒有就讓規格軸回報「no spec available」並註記
兩軸發現互相矛盾（一過一掛）這正是雙軸設計要捕捉的正常情況不要跨軸排序，並排呈現即可；由開發者決定先修哪一軸
子代理報告裡出現「無法確認」子代理沒拿到完整 diff 或規範來源清單規範軸必須把 smell baseline 完整貼入提示，規格軸必須附規格全文——子代理沒有其他存取路徑

🏆 進階挑戰題

  1. 固定點語義：解釋 git diff main...HEAD 與 git diff main..HEAD 的差異，並說明在「review 我的分支」與「review 合併後的結果」兩種意圖下各該用哪個。
  2. 壞味道分類：給你三個 diff 片段（a）同名邏輯在兩個檔案重複（b）方法大量讀取別物件的欄位（c）一個 300 行的 switch 在多處出現。分別對應哪個 Fowler 壞味道、該怎麼修？
  3. 範圍蔓延偵測：規格只要「加一個欄位」，但 PR 同時重構了 serializer。規格軸該如何回報？規範軸又該如何回報？兩軸各自獨立，不互相代答。

🏗️ 專案級端到端 Worked Example

專案情境：一個完整的「會員帳單重構」專案——把帳單模組從 15 個散落的函式重構成深模組，分三張 ticket 合併回 main。code-review 在每一張 PR 與最終合併時各扮演不同角色。

  1. Ticket 1 PR：固定點 git diff main...feature/billing-core，規格來源是 .scratch/billing-refactor/issues/01-consolidate-billing.md。規範軸抓到 any 洩漏（違反 CODING_STANDARDS.md）、規格軸確認「集中計費邏輯」已完整。
  2. 修復往返：開發者依兩軸報告修正 → 重新 /code-review，直到規範軸與規格軸都乾淨 → 合併。
  3. Ticket 2 PR：固定點 git diff main...feature/billing-rates。這次 commit message 有 Closes #310，規格從 issue 拉取。規範軸抓到「重複 switch」壞味道（新的費率計算在多處重複 if-else）；規格軸抓到大範圍蔓延——PR 順手改了 serializer。
  4. Ticket 3 PR：固定點 git diff main...feature/billing-migration，這是資料遷移 ticket。規範軸對照 docs/adr/ 確認遷移方式符合 ADR-0009；規格軸逐條核對遷移清單。
  5. 最終合併前：對 git diff merge-base(main, feature) ... main 跑一次全量 review，確認三張 ticket 合併後整體沒有跨 ticket 的互動錯誤（例如 Ticket 2 的費率計算被 Ticket 3 的遷移邏輯誤改）。

預期輸出：每張 PR 一張雙軸報告（## Standards / ## Spec 並排）＋一行摘要（各軸發現數與最嚴重問題）。三張 PR 都通過後，main 進入可發佈狀態。

關鍵設計：review 的固定點「跟著 ticket 移動」是專案級的關鍵——每張 ticket 的 diff 只含該 ticket 的變更，規格軸才能精準對照。最後的全量 review 是補「垂直切片各自綠、合併後才看到的互動問題」的洞。

⚙️ 效能 / 品質 / 安全深度

效能：兩個平行子代理讓審查時間接近「單軸時間」而非「雙軸時間」。效能瓶頸常在 diff 大小——一個 2000 行的 diff 會讓子代理在殘缺輸入上做判斷。實務上用 git diff --stat 先看規模，diff 過大時請開發者拆成多個小 PR，讓 review 品質不因規模稀釋。

品質：品質的核心機制是雙軸分離——不跨軸排序、不互相掩蓋。規範軸的 smell baseline 保證「repo 沒文件也有最低標準」；規格軸靠「逐條引用規格原文」把「做對」與「做錯」變成可對照的檢查。報告品質的驗收標準：每一條發現都能被另一個人獨立複核（引用標準/規格原文）。

安全：審查是安全漏洞進 codebase 的最後一道閘門。除了兩個軸，實務上要在規範軸補「安全檢查」子清單：diff 是否新增 secret 或硬編碼金鑰（git diff | grep -i "api[_-]key\|password\|secret"）、是否繞過既有認證/授權路徑、錯誤訊息是否洩漏內部細節（stack trace、SQL）。這些不寫進技能文件，但 review 執行者應在審查時主動檢視——審查者的安全敏感度就是最後防線。

🏗️ ① 專案級端到端 Worked Example

專案情境：你在一個有 50 個檔案變更的 PR 上跑 code-review，需要同時驗證規範和規格。

  1. 先用 /code-review --base main 跑規範軸（coding standards）：檢查命名、格式、error handling、import 順序。
  2. 同時跑規格軸（spec compliance）：對照原始 issue 的 acceptance criteria，逐條驗證。
  3. 兩軸結果並排呈現：規範問題（3 個 warning）和規格問題（1 個遺漏）。
  4. 規範問題可以自動修（Prettier + ESLint），規格問題需要人工判斷——code-review 會標出「需確認」vs「可自動修」。

關鍵：規範軸是「怎麼寫」，規格軸是「寫對了沒」。兩者平行跑、分開報告，才不會混淆「風格問題」和「功能遺漏」。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能大 PR（200+ 檔案）的 review 時間隨檔案數線性成長。建議先用 git diff --stat 篩出核心變更，再跑 code-review。
品質規範軸的誤報率（false positive）通常高於規格軸。把 linting 當作規範軸的預處理，可減少人工覆判的負擔。
安全Code review 是防禦 SQL injection、XSS、secrets leak 的最後一道關卡。在規範軸加入 security checklist（如 no-eval、no-innerHTML）可自動攔截。
