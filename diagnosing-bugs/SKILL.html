Diagnosing Bugs

診斷 Bug

A discipline for hard bugs. Skip phases only when explicitly justified.

一套應付硬 bug 的紀律。只有明確證成時才可跳過階段。

When exploring the codebase, read CONTEXT.md (if it exists) to get a clear mental model of the relevant modules, and check ADRs in the area you're touching.

探索程式碼時，先讀 CONTEXT.md（如果存在）以取得相關模組的清晰心智模型，並檢查你要觸及的區域中的 ADR。

Phase 1 — Build a feedback loop

第一階段——建立回饋迴圈

This is the skill. Everything else is mechanical. If you have a tight pass/fail signal for the bug — one that goes red on this bug — you will find the cause; bisection, hypothesis-testing, and instrumentation all just consume it. If you don't have one, no amount of staring at code will save you.

這就是本技能的核心。 其他一切都是機械性作業。如果你對這個 bug 有一個緊密的通過/失敗訊號——一個會因為_這個_ bug 而變紅的訊號——你就會找到原因；二分、假設檢驗與插樁都只是在消耗它。如果你沒有這樣的訊號，再怎麼瞪著程式碼看也救不了你。

Spend disproportionate effort here. Be aggressive. Be creative. Refuse to give up.

在這裡投入不成比例的精力。要積極。要有創意。拒絕放棄。

Ways to construct one — try them in roughly this order

建立回饋迴圈的方法——大致依此順序嘗試

  1. Failing test at whatever seam reaches the bug — unit, integration, e2e.
  2. Curl / HTTP script against a running dev server.
  3. CLI invocation with a fixture input, diffing stdout against a known-good snapshot.
  4. Headless browser script (Playwright / Puppeteer) — drives the UI, asserts on DOM/console/network.
  5. Replay a captured trace. Save a real network request / payload / event log to disk; replay it through the code path in isolation.
  6. Throwaway harness. Spin up a minimal subset of the system (one service, mocked deps) that exercises the bug code path with a single function call.
  7. Property / fuzz loop. If the bug is "sometimes wrong output", run 1000 random inputs and look for the failure mode.
  8. Bisection harness. If the bug appeared between two known states (commit, dataset, version), automate "boot at state X, check, repeat" so you can git bisect run it.
  9. Differential loop. Run the same input through old-version vs new-version (or two configs) and diff outputs.
  10. HITL bash script. Last resort. If a human must click, drive them with scripts/hitl-loop.template.sh so the loop is still structured. Captured output feeds back to you.
  1. 失敗測試，在任何觸及 bug 的接縫——單元、整合、e2e。
  2. curl / HTTP 腳本，對著正在執行的開發伺服器。
  3. CLI 呼叫，搭配固定裝置輸入，把 stdout 跟已知良好快照做 diff。
  4. 無頭瀏覽器腳本（Playwright / Puppeteer）——驅動 UI，對 DOM / 主控台 / 網路做斷言。
  5. 重播擷取的追蹤。把真實的網路請求 / payload / 事件日誌存到磁碟；在隔離環境中透過程式碼路徑重播。
  6. 一次性測試架。啟動系統的最小子集合（一個服務、模擬過的相依），用單一函式呼叫去觸發 bug 的程式碼路徑。
  7. 屬性 / 模糊測試迴圈。如果 bug 是「輸出偶爾錯誤」，跑 1000 個隨機輸入，找出失敗模式。
  8. 二分測試架。如果 bug 出現在兩個已知狀態之間（commit、資料集、版本），自動化「在狀態 X 啟動、檢查、重複」，讓你能 git bisect run。
  9. 差異迴圈。把相同輸入跑過舊版 vs 新版（或兩種設定），diff 輸出。
  10. HITL bash 腳本。最後手段。如果必須由人點擊，用 scripts/hitl-loop.template.sh 驅動_他們_，讓迴圈仍然結構化。擷取的輸出會回饋給你。

Build the right feedback loop, and the bug is 90% fixed.

建立正確的回饋迴圈，bug 就完成九成了。

Tighten the loop

收緊迴圈

Treat the loop as a product. Once you have a loop, tighten it:

把迴圈當產品來經營。一旦有了_一個_迴圈，就收緊它：

  • Can I make it faster? (Cache setup, skip unrelated init, narrow the test scope.)
  • Can I make the signal sharper? (Assert on the specific symptom, not "didn't crash".)
  • Can I make it more deterministic? (Pin time, seed RNG, isolate filesystem, freeze network.)
  • 能不能讓它更快？（快取設定、跳過無關的初始化、縮小測試範圍。）
  • 能不能讓訊號更銳利？（斷言具體症狀，而不是「沒有崩潰」。）
  • 能不能讓它更確定？（釘住時間、播種 RNG、隔離檔案系統、凍結網路。）

A 30-second flaky loop is barely better than no loop; a 2-second deterministic one is tight — a debugging superpower.

一個要花 30 秒的搖擺迴圈只比沒有迴圈好一點點；一個 2 秒且確定的是緊密的——這是除錯的超能力。

Non-deterministic bugs

非確定性 bug

The goal is not a clean repro but a higher reproduction rate. Loop the trigger 100×, parallelise, add stress, narrow timing windows, inject sleeps. A 50%-flake bug is debuggable; 1% is not — keep raising the rate until it's debuggable.

目標不是乾淨的重現，而是更高的重現率。把觸發器重複 100 次、平行化、加壓力、收窄時間窗、注入 sleep。50% 會搖擺的 bug 可以除錯；1% 的不能——持續拉高重現率，直到它能被除錯。

When you genuinely cannot build a loop

當你真的無法建立迴圈

Stop and say so explicitly. List what you tried. Ask the user for: (a) access to whatever environment reproduces it, (b) a captured artifact (HAR file, log dump, core dump, screen recording with timestamps), or (c) permission to add temporary production instrumentation. Do not proceed to hypothesise without a loop.

停下來，明確說出來。列出你試過什麼。向使用者要求：(a) 存取能重現它的任何環境，(b) 一個擷取的產物（HAR 檔、日誌傾倒、核心傾倒、帶時間戳的螢幕錄影），或 (c) 加入暫時正式環境插樁的權限。不要在沒有迴圈的情況下繼續做假設。

Completion criterion — a tight loop that goes red

完成標準——一個會變紅的緊密迴圈

Phase 1 is done when the loop is tight and red-capable: you can name one command — a script path, a test invocation, a curl — that you have already run at least once (paste the invocation and its output), and that is:

第一階段完成的條件是迴圈緊密且能變紅：你能指認出一個指令——一個腳本路徑、一次測試呼叫、一個 curl——你至少已經跑過一次（貼出該呼叫及其輸出），而且它：

  • [ ] Red-capable — it drives the actual bug code path and asserts the user's exact symptom, so it can go red on this bug and green once fixed. Not "runs without erroring" — it must be able to catch this specific bug.
  • [ ] Deterministic — same verdict every run (flaky bugs: a pinned, high reproduction rate, per above).
  • [ ] Fast — seconds, not minutes.
  • [ ] Agent-runnable — you can run it unattended; a human in the loop only via scripts/hitl-loop.template.sh.
  • [ ] 能變紅——它驅動真正的 bug 程式碼路徑，並斷言使用者的確切症狀，所以它會因為這個 bug 而變紅、修好後變綠。不是「跑起來沒有報錯」——它必須能_抓到這個特定 bug_。
  • [ ] 確定——每次執行結果相同（搖擺 bug：釘住的高重現率，如上述）。
  • [ ] 快速——幾秒，不是幾分鐘。
  • [ ] 代理可執行——你可以無人看管地跑它；只有透過 scripts/hitl-loop.template.sh 才需要人在迴圈中。

If you catch yourself reading code to build a theory before this command exists, stop — jumping straight to a hypothesis is the exact failure this skill prevents. No red-capable command, no Phase 2.

如果你發現自己在這個指令存在之前就讀程式碼建理論，停下來——直接跳到假設正是本技能要防止的失敗模式。 沒有能變紅的指令，就沒有第二階段。

Phase 2 — Reproduce + minimise

第二階段——重現 + 最小化

Run the loop. Watch it go red — the bug appears.

執行迴圈。看它變紅——bug 出現了。

Confirm:

確認：

  • [ ] The loop produces the failure mode the user described — not a different failure that happens to be nearby. Wrong bug = wrong fix.
  • [ ] The failure is reproducible across multiple runs (or, for non-deterministic bugs, reproducible at a high enough rate to debug against).
  • [ ] You have captured the exact symptom (error message, wrong output, slow timing) so later phases can verify the fix actually addresses it.
  • [ ] 迴圈產生的是使用者描述的那個失敗模式——不是碰巧在附近的其他失敗。錯誤的 bug = 錯誤的修復。
  • [ ] 失敗在多次執行間可重現（或對非確定性 bug，重現率高到足以針對它除錯）。
  • [ ] 你已擷取確切的症狀（錯誤訊息、錯誤輸出、緩慢的時序），讓後續階段可以驗證修復確實對症下藥。

Minimise

最小化

Once it's red, shrink the repro to the smallest scenario that still goes red. Cut inputs, callers, config, data, and steps one at a time, re-running the loop after each cut — keep only what's load-bearing for the failure.

一旦它變紅，把重現縮到仍會變紅的最小情境。一次一個地砍掉輸入、呼叫者、設定、資料與步驟，每次砍完重跑迴圈——只保留對失敗真正承重的東西。

Why bother: a minimal repro shrinks the hypothesis space in Phase 3 (fewer moving parts left to suspect) and becomes the clean regression test in Phase 5.

為什麼要費心：最小重現會縮小第三階段的假設空間（剩下可懷疑的活動部件更少），並成為第五階段的乾淨回歸測試。

Done when every remaining element is load-bearing — removing any one of them makes the loop go green.

完成條件是每個剩餘元素都承重——移除任何一個都會讓迴圈變綠。

Do not proceed until you have reproduced and minimised.

在完成重現與最小化之前，不要往下走。

Phase 3 — Hypothesise

第三階段——提出假設

Generate 3–5 ranked hypotheses before testing any of them. Single-hypothesis generation anchors on the first plausible idea.

在測試任何假設之前，產生 3–5 個排序的假設。單一假設容易錨定在第一個看起來合理的想法上。

Each hypothesis must be falsifiable: state the prediction it makes.

每個假設都必須可否證：說出它做出的預測。

Format: "If is the cause, then will make the bug disappear / will make it worse."

格式：「如果 是原因，那麼 <改變 Y> 會讓 bug 消失 / <改變 Z> 會讓它更糟。」

If you cannot state the prediction, the hypothesis is a vibe — discard or sharpen it.

如果你說不出預測，那假設只是一種感覺——丟棄它或把它磨利。

Show the ranked list to the user before testing. They often have domain knowledge that re-ranks instantly ("we just deployed a change to #3"), or know hypotheses they've already ruled out. Cheap checkpoint, big time saver. Don't block on it — proceed with your ranking if the user is AFK.

在測試之前，把排序後的清單給使用者看。 他們通常擁有能立刻重新排序的領域知識（「我們剛剛部署了 #3 的改動」），或知道他們已經排除的假設。便宜的檢查點，省下大把時間。不要被它卡住——如果使用者 AFK，就照你的排序往下走。

Phase 4 — Instrument

第四階段——插樁

Each probe must map to a specific prediction from Phase 3. Change one variable at a time.

每個探針都必須對應到第三階段的特定預測。一次只改一個變數。

Tool preference:

工具偏好：

  1. Debugger / REPL inspection if the env supports it. One breakpoint beats ten logs.
  2. Targeted logs at the boundaries that distinguish hypotheses.
  3. Never "log everything and grep".
  1. 除錯器 / REPL 檢視，如果環境支援的話。一個中斷點勝過十個日誌。
  2. 具針對性的日誌，放在能區分假設的邊界上。
  3. 永遠不要「全部打日誌然後 grep」。

Tag every debug log with a unique prefix, e.g. [DEBUG-a4f2]. Cleanup at the end becomes a single grep. Untagged logs survive; tagged logs die.

用獨特前綴標記每個除錯日誌，例如 [DEBUG-a4f2]。最後的清理變成單次 grep。未標記的日誌存活；標記的日誌陣亡。

Perf branch. For performance regressions, logs are usually wrong. Instead: establish a baseline measurement (timing harness, performance.now(), profiler, query plan), then bisect. Measure first, fix second.

效能分支。 對效能回歸，日誌通常是錯的。改成：先建立基線量測（時序測試架、performance.now()、profiler、查詢計畫），再二分。先量測，後修復。

Phase 5 — Fix + regression test

第五階段——修復 + 回歸測試

Write the regression test before the fix — but only if there is a correct seam for it.

在修復之前寫回歸測試——但只有當它有正確的接縫時。

A correct seam is one where the test exercises the real bug pattern as it occurs at the call site. If the only available seam is too shallow (single-caller test when the bug needs multiple callers, unit test that can't replicate the chain that triggered the bug), a regression test there gives false confidence.

正確的接縫是測試在呼叫點實際發生的 bug 模式上運作的接縫。如果唯一可用的接縫太淺（bug 需要多個呼叫者時卻只有單一呼叫者測試、無法重現觸發 bug 的鏈的單元測試），在那裡的回歸測試會給你錯誤的信心。

If no correct seam exists, that itself is the finding. Note it. The codebase architecture is preventing the bug from being locked down. Flag this for the next phase.

如果沒有正確的接縫，那本身就是發現。 記下它。程式庫架構正在阻止 bug 被鎖定。把這個標記給下一階段。

If a correct seam exists:

如果正確的接縫存在：

  1. Turn the minimised repro into a failing test at that seam.
  2. Watch it fail.
  3. Apply the fix.
  4. Watch it pass.
  5. Re-run the Phase 1 feedback loop against the original (un-minimised) scenario.
  1. 把最小化的重現變成該接縫上的失敗測試。
  2. 看它失敗。
  3. 套用修復。
  4. 看它通過。
  5. 針對原始（未最小化）情境重跑第一階段的回饋迴圈。

Phase 6 — Cleanup + post-mortem

第六階段——清理 + 事後檢討

Required before declaring done:

宣告完成前必須完成：

  • [ ] Original repro no longer reproduces (re-run the Phase 1 loop)
  • [ ] Regression test passes (or absence of seam is documented)
  • [ ] All [DEBUG-...] instrumentation removed (grep the prefix)
  • [ ] Throwaway prototypes deleted (or moved to a clearly-marked debug location)
  • [ ] The hypothesis that turned out correct is stated in the commit / PR message — so the next debugger learns
  • [ ] 原始重現不再重現（重跑第一階段迴圈）
  • [ ] 回歸測試通過（或接縫缺失已記錄在案）
  • [ ] 所有 [DEBUG-...] 插樁已移除（grep 該前綴）
  • [ ] 一次性原型已刪除（或移到清楚標記的除錯位置）
  • [ ] 正確的假設寫進 commit / PR 訊息——讓下一位除錯者學到

Then ask: what would have prevented this bug? If the answer involves architectural change (no good test seam, tangled callers, hidden coupling) hand off to the /improve-codebase-architecture skill with the specifics. Make the recommendation after the fix is in, not before — you have more information now than when you started.

然後問：什麼能防止這個 bug？ 如果答案涉及架構變更（沒有好的測試接縫、呼叫者糾纏不清、隱藏的耦合），把具體內容交接給 /improve-codebase-architecture 技能。在修復完成之後再提出建議，不要提前——你現在比開始時擁有更多資訊。

📖 教學解說

diagnosing-bugs 的核心哲學是：先有迴圈，再談假設。大多數除錯的失敗來自「直接跳到假設」——你猜了一個原因，花時間追下去，結果猜錯了。這個技能強制你先建立一個會變紅的緊密迴圈（一個指令能重現 bug），然後才開始猜。

六個階段的順序很關鍵：(1) 建迴圈 → (2) 重現+最小化 → (3) 假設 → (4) 插樁 → (5) 修復+回歸測試 → (6) 清理+事後檢討。每個階段都有明確的完成標準——沒有通過就不能往下走。

💡 Worked Example

情境：用戶回報「偶爾會收到空的 CSV 匯出」，但你無法重現。

  1. Phase 1：建立迴圈。寫一個腳本 test-export.sh：curl -s /api/export?start=2024-01-01 | head -5。跑 100 次，發現有 3 次回傳空結果。迴圈建立了——重現率 3%。
  2. Phase 2：最小化。砍掉日期篩選參數 → 仍然 3%。砍掉 header → 仍然 3%。發現跟並發有關——兩個同時請求時更容易觸發。最小重現：for i in {1..10}; do curl -s /api/export & done; wait。
  3. Phase 3：提出 3 個假設：(a) 共用 cursor 沒有 thread safety (b) 記憶體不足 (c) 超時。展示給使用者看——使用者說「我們上週改了 cursor pooling」→ 假設 (a) 排第一。
  4. Phase 4：插樁。加 [DEBUG-cursor] 日誌在 cursor 初始化處，確認是否有 race condition。
  5. Phase 5：修復。加 mutex 保護 cursor 初始化。回歸測試通過。

⚠️ 常見錯誤

  • 直接跳到假設——「我覺得是 race condition」→ 花兩小時追，結果不是。技能要求先有迴圈再猜。
  • 迴圈太慢——一個要跑 30 秒的迴圈只比沒有好一點。目標是幾秒內完成。
  • 沒有最小化就開始假設——最小化能縮小假設空間。未最小化 = 更多活動部件 = 更多可能原因。
  • 一個假設就開始測——單一假設容易錨定。先列出 3–5 個排序的假設，展示給使用者看。

✅ 練習 / 驗收清單

  • □ 迴圈能在幾秒內完成
  • □ 迴圈是確定性的（或有高重現率）
  • □ 迴圈能變紅（不是「跑起來沒有報錯」）
  • □ 最小化後每個剩餘元素都承重
  • □ 有 3–5 個排序的假設，且每個都可否證
  • □ 測試前把假設清單展示給使用者看
  • □ 修復後有回歸測試
  • □ 清理了所有插樁（grep 確認）

🚀 進階真實情境 Worked Example

情境：用戶回報「匯出功能在某個時段特別慢，有時直接 504」，但開發環境完全無法重現。

  1. Phase 1 建迴圈：開發環境無法重現 → 抓不到真實症狀。改為重播追蹤：把正式環境的一筆慢請求的 HAR / trace 存到磁碟，寫一個 harness 重播同一筆 payload 進隔離的匯出程式碼路徑 → 它在本地穩定地慢了 40 秒，迴圈建立。
  2. 收緊迴圈：把時間窗縮小到只量測「CSV 序列化」而非整個 HTTP 層，速度從 40 秒降到 3 秒。
  3. Phase 2 最小化：逐一砍掉欄位，發現只要包含某個多層 JSON 欄位就慢——最小重現是「含嵌套 JSON 的單筆紀錄」。每個剩餘元素都承重。
  4. Phase 3 假設：(a) 序列化用遞迴展平造成指數爆炸（b) 欄位值被重複解析多次（c) 資料庫查詢 N+1。展示給使用者——他們說「我們這週把 JSON 欄位從 SELECT 改成邊讀邊 parse」→ 假設 (b) 升到第一。
  5. Phase 4 插樁：在 parse 處加 [DEBUG-json] 計數，確認同一個欄位被 parse 了 5 次（一次一次地 parse，而非讀一次用多次）。
  6. Phase 5–6：回歸測試鎖定「同欄位只 parse 一次」，修復後重播原始 trace 確認從 40 秒回到 2 秒；移除全部插樁。

設計決策：本例與初階範例（空 CSV）最大的不同是開發環境無法重現。重點不是執著於「在本地重現」，而是「拿到能觸發 bug 的輸入」——用重播真實 trace 的方式把正式環境的輸入帶進本地，迴圈照樣建立。這是 Phase 1 的「重播擷取追蹤」技巧在真實世界的典型用法。

🔬 深入原理擴充

「先建迴圈再談假設」背後是科學方法論裡的可證偽性原則。假設本身沒有價值，假設的預測才有——而預測必須能被一次實驗判死。本技能把它形式化為「迴圈能變紅」：一個不能變紅的迴圈，代表你連「bug 的具體定義」都還沒抓到，任何假設都是空想。這也是為什麼 Phase 2 要求確認「是使用者描述的那個失敗模式」，而不是碰巧在附近的其他失敗——抓錯 bug 的假設再多也白搭。

對 AI coding assistant 而言，這個紀律對抗的是模型最容易犯的錯誤：模式匹配式的猜測。模型看到「效能慢」就聯想到「N+1 查詢」，然後開始翻程式碼找證據——這是把結論當前提。技能強制你先找到「一條保證會紅的指令」，從根上斷絕這種倒果為因。

陷阱案例：很多人以為「加了一堆 console.log 就叫插樁」。但「log everything and grep」正是 Phase 4 明令禁止的——無差別日誌產生的資料太多，反而稀釋掉能區分假設的那一條線索。更糟的是未標記的日誌會在修復後殘留在正式環境。真相是：插樁的數量要最少、位置要精準——每個探針對應 Phase 3 的一個具體預測，且必須帶 [DEBUG-xxx] 前綴讓清理變成單次 grep。

🏆 進階挑戰題

  1. 迴圈設計：一個「偶爾（約 3%）訂單金額計算錯誤」的 bug。設計一個能提高到可除錯重現率的迴圈（提示：平行化、固定種子、收窄時間窗）。寫出具體指令。
  2. 假設可否證：假設「是 cache 未失效造成的」。把這句話改寫成可否證的形式：「如果 X 是原因，那麼改變 Y 會讓 bug 消失／改變 Z 會讓它更糟。」並說明該插哪個樁。
  3. 接縫判斷：bug 需要多個呼叫者同時觸發，但唯一可測的接縫只有單一呼叫者。根據 Phase 5，這說明什麼？你該在回歸測試上做什麼、該交接給誰？

🏗️ 專案級端到端 Worked Example

專案情境：一個「訂單匯出服務」的完整事故處理專案——線上偶發 504＋部分訂單遺漏，你負責用 diagnosing-bugs 的六階段從頭到尾修完，並把教訓回饋進專案。

  1. Phase 1 建迴圈：開發環境重現不了 → 用「重播擷取追蹤」把正式環境的慢請求 trace 存下來，寫 harness 在隔離路徑重播 → 穩定重現「含大 JSON 欄位時序列化慢 40 秒、部分訂單被截斷」。迴圈：node replay.js --trace trace-1042.json，2 秒內給紅。
  2. Phase 2 最小化：逐一砍欄位/呼叫者，最小重現縮到「單筆含嵌套 JSON 的訂單」。每個剩餘元素都承重。
  3. Phase 3 假設：列出 4 個可否證假設並排序（重複解析 JSON、序列化指數爆炸、N+1 查詢、記憶體不足）；展示給使用者，對方說「我們上週把 JSON 欄位改成邊讀邊 parse」→ 重複解析升到第一。
  4. Phase 4 插樁：在 parse 點加 [DEBUG-json] 計數，確認同一欄位被 parse 5 次。
  5. Phase 5 修復＋回歸：先寫回歸測試鎖定「同欄位只 parse 一次」（接縫：序列化函式公開介面）→ 看它紅 → 修 → 綠 → 重播原始 trace 確認 40 秒回到 2 秒、無訂單遺漏。
  6. Phase 6 事後檢討：清理插樁（grep [DEBUG-）、把正確假設寫進 commit。發現「序列化模組沒有好接縫」→ 交接給 /improve-codebase-architecture 深化候選。

預期輸出：一個回歸測試＋一個修復 commit＋一段寫進 commit 的事後檢討＋一張交給架構改善的深化候選。整起事故從「無法重現」到「被測試鎖住」。

關鍵設計：全案的「迴圈」只有一個（replay.js），但它在每個階段被不同方式消耗——最小化砍輸入、假設驗證看計數、回歸測試當基準。迴圈先於一切，這就是本技能的核心。

⚙️ 效能 / 品質 / 安全深度

效能：診斷本身就是效能工作——迴圈的速度決定除錯速度。Phase 4 對效能回歸有專屬分支：「日誌通常是錯的，先建立基線量測再二分」。實務上把量測做成 script（perf-baseline.sh），每次修改後重跑，把「效能」變成「可二分的事實」而非「感覺」。

品質：品質保證來自回歸測試的接縫正確性——測試必須在「真實 bug 模式發生的呼叫點」運作，否則給的是錯誤信心。若沒有正確接縫，「那本身就是發現」——這比「貼一個假測試」更誠實，也是交接給架構改善的正確起點。

安全：事故處理常夾帶安全風險：(1) 插樁若打在正式環境，日誌可能記錄敏感 payload——[DEBUG-json] 前綴讓清理變成單次 grep，且插樁內容絕不列印訂單個資；(2) 修復時為了「快速止血」容易繞過既有授權——修完後必須跑 /code-review 的安全檢查確認沒開旁路；(3) 若事故是安全事件（資料洩漏、未授權存取），Phase 6 的事後檢討要額外寫「防範機制」而非只是「修復方法」。

🏗️ ① 專案級端到端 Worked Example

專案情境：使用者回報「API 回應時間從 200ms 暴增到 3s」，你需要定位根因。

  1. 先跑 /diagnosing-bugs，收集症狀：哪些 endpoint 變慢？是所有請求還是特定參數？是最近才變慢嗎？
  2. 建立假說：可能是 N+1 query、可能是 cache miss、可能是新版本的 regression。
  3. 設計最小實驗：跑 EXPLAIN ANALYZE 確認是否有 N+1、檢查 cache hit rate、比對新舊版本的 query plan。
  4. 驗證根因：假說被證實後，用 git bisect 定位引入 regression 的 commit。
  5. 修復並確認：修復後跑 /tdd 加一迴歸測試，確保不會再發生。

關鍵：診斷迴圈的核心是「假說→實驗→驗證」，不是「猜→改→試」。每個假說都要有可量化的驗證方式。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能診斷迴圈本身有「偵測成本」：每次假說驗證都要跑實驗。用 git bisect 可在 O(log n) 內定位 regression，比逐 commit 測試快得多。
品質「修了但沒加迴歸測試」是 diagnose 最常見的遺漏。確保每個修復都伴隨一個「之前會壞、現在不會」的測試。
安全診斷過程中可能需要跑 git reset --hard 或 git stash——確保在安全分支上操作，避免丟失未 commit 的變更。
