Its job:

它的工作：

  1. Investigate the question against primary sources — official docs, source code, specs, first-party APIs — not a secondary write-up of them. Follow every claim back to the source that owns it.
  2. Write the findings to a single Markdown file, citing each claim's source.
  3. Save it where the repo already keeps such notes; match the existing convention, and if there is none, put it somewhere sensible and say where.

📖 教學解說

research 是委派閱讀苦工的技能。它的設計是：你問一個問題，agent 在背景調查主要來源（官方文件、原始碼、規格、第一方 API），產出一份有引用的 Markdown 報告。你不用等它——它在背景跑，你可以繼續做其他事。

關鍵約束：只信主要來源。不要信二手轉述、部落格文章、Stack Overflow 回答。每一項主張都要追回到擁有它的來源。這是為了確保研究報告的可信度。

💡 Worked Example

情境：你要決定 CSV 匯出該用 streaming 還是 batch，需要了解 Node.js 的 Stream API。

  1. 呼叫 /research "Node.js Readable Stream 在大資料量下的記憶體行為"
  2. Agent 在背景調查：
    • Node.js 官方文件的 Stream 章節（主要來源）
    • Node.js 原始碼中 highWaterMark 的實作（主要來源）
  3. 產出報告：`research/nodejs-stream-memory.md`，引用了官方文件和原始碼
  4. 你拿到報告後，決策有根有據

⚠️ 常見錯誤

  • 信二手來源——部落格文章、Medium、Stack Overflow 都是二手轉述。Research 只信主要來源。
  • 沒有引用——報告裡的每個主張都該有來源連結。沒有引用 = 沒有可信度。
  • 把 research 當成取代思考——Research 餵養思考，不是取代思考。拿到報告後，你還是要做決策。
  • 問題太廣——「研究 Node.js」太廣。要精準：「Node.js Readable Stream 在大資料量下的記憶體行為」。

✅ 練習 / 驗收清單

  • □ 問題精準、範圍明確
  • □ 報告只引用主要來源（官方文件、原始碼、規格）
  • □ 每個主張都有來源連結
  • □ 報告存在 repo 的合理位置
  • □ 拿到報告後有做後續決策

🚀 進階真實情境 Worked Example

情境：你的團隊要在現有 Node.js API 加入「webhook 簽章驗證」，你只知道「要用 HMAC」，但不想憑印象選演算法——讓 research 去查清事實。

  1. 精準提問：/research "GitHub webhook 的 HMAC 簽章驗證規格：header 名稱、payload 格式、常數時間比較的實作要求"。
  2. 背景代理只查主要來源：GitHub 官方 docs 的 webhook 章節（header 叫 X-Hub-Signature-256、payload 是 raw body、前綴 sha256=）、Node.js crypto 官方文件（crypto.timingSafeEqual 的用途與限制）。
  3. 報告 research/webhook-hmac.md 逐條引用來源。你發現一個關鍵事實：timingSafeEqual 要求兩邊 input 等長，否則要先 hash 才能比較——這正是最容易被寫錯的地方。
  4. 你帶著報告進 grill-with-docs，把「用 X-Hub-Signature-256 + timingSafeEqual + 先 hash 再比較」的決策寫進 CONTEXT.md 與實作 spec。
  5. implement 時，報告裡的引用讓 code-review 的規範軸有據可查——「為什麼這樣寫」都有官方文件背書。

設計決策：本例的關鍵是「先 hash 再比較」這種安全細節不在任何人的參數式知識裡可靠存在——正是 research 該出場的地方。同時注意：research 沒有替你決定「該用 GitHub 規格」，它只查「GitHub 規格是什麼」。決策（採用 GitHub 規格）是你做的。

🔬 深入原理擴充

research 對抗的是 LLM 的參數式知識——模型在預訓練中「記住」的事實。這些事實大部分正確，但會在細節處失準（版本、參數名、行為差異），而且模型「很有自信地錯」。技能強制「只信主要來源」正是把信任從「參數式記憶」轉移到「可驗證的文檔」。

「把每項主張追回擁有它的來源」是引用責任制：一份研究報告的可信度，等於它的引用可被逐一驗證的程度。這也讓後續技能受益——code-review 的規格軸、implement 的決策，都能沿著引用鏈追溯到官方文件。

陷阱案例：很多人以為「找一堆文件＝research」，於是指望一份報告裡塞滿二十個連結就完事。真相是：連結多不代表可信，來源層級才是關鍵——官方文件的一行，勝過十篇部落格轉述。更糟的是把 Stack Overflow 回答當「事實來源」，而它常常是過時或錯誤的。判斷原則是：這個來源「擁有」這項主張嗎？官方 docs 擁有 API 行為、原始碼擁有實作細節；部落格只是轉述，不擁有任何主張。

🏆 進階挑戰題

  1. 來源分級：給你四個來源——官方 API 文件、GitHub 上的 issue 討論、熱門部落格教學、原始碼註解。為「某函式的行為」排序可信度，並說明各該在什麼情境下使用。
  2. 提問收窄：把「研究 Node.js 效能」這個過廣的問題，改寫成三個適合 research 的精準子題，並各標出應該查的主要來源。
  3. 引用責任制：寫出一份 3 行的研究結論，主題「Prisma 的 connection pool 預設值」，每行都要有具體引用。然後說明這份結論能如何被 code-review 的規格軸使用。

🏗️ ① 專案級端到端 Worked Example

專案情境：你要選擇一個 state management 方案（Redux vs Zustand vs Jotai），需要有根據的比較。

  1. 先跑 /research，定義研究問題：「在 React 18 + TypeScript 的大型 SPA 中，哪個 state management 方案的效能、DX、維護性最好？」
  2. research 會從高可信度來源蒐集資料：官方文件、benchmark、真實專案的案例研究（不是部落格文章）。
  3. 產出比較報告：表格對比三者的 bundle size、學習曲線、SSR 支援、DevTools 支援、社群活躍度。
  4. 把報告寫進 repo 的 docs/research-state-management.md，連結到相關的 issue。這份文件可以被 /to-spec 引用。

關鍵：research 的價值在「可信度」——它只用主要來源（官方文件、benchmark），不用次要來源（部落格、社群討論）。文件的可信度取決於來源的品質。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能research 的 token 成本與來源數量成正比。限制在 5-10 個高可信度來源，避免「什麼都看」導致 token 爆炸。
品質報告的品質取決於「問題是否夠明確」。模糊的問題（「哪個 state management 好」）產出模糊的答案；具體的問題（「在 React 18 的 SSR 場景中，Zustand 和 Redux 的 hydration 策略有什麼不同」）產出有用的比較。
安全研究報告可能揭露安全相關的資訊（例如某個 library 有 known vulnerabilities）——確保把這些記在報告的安全章節中。
