to-questionnaire

你自己答不了的決策，變成能答的人來填的問卷。

Turn something the user can't answer alone into a questionnaire — a Markdown document they hand to one person to fill in async, or fill out together over a meeting. The recipient holds knowledge the user lacks; the questionnaire pulls it out of them.

將一個使用者無法獨自回答的事情轉化為一份問卷 — 一份 Markdown 文件，他們把它交給一個人非同步填寫，或在會議中一起填寫。收件人握有使用者缺乏的知識；問卷把它從他們身上引出來。

Grill the send, not the subject. Interview the user only about the send, which they can always answer: who it goes to, and what they need back. The questions in the document then target the gap between what the recipient knows and what the user needs.

質詢的是寄送，不是主題。 只訪問使用者關於_寄送_的事，這他們總是能回答：寄給誰，以及他們需要回覆什麼。文件中的問題然後針對收件人所知與使用者所需之間的缺口。

  1. Who is it going to? Ask, in one exchange, the recipient's role, expertise, and relationship to the user. This fixes the questionnaire's tone and how much context it must carry. Done when you know who the recipient is and what they know that the user doesn't.
  1. 要寄給誰？ 在一個來回中詢問收件人的角色、專業以及與使用者的關係。這決定了問卷的語氣以及它必須承載多少脈絡。當您知道收件人是誰以及他們知道什麼使用者不知道的事時，就完成了。
  1. What do you need back? Ask, in one exchange, the specific decisions or facts the user can't resolve alone and needs from this person. Done when you have a concrete list of what the user must walk away able to do or decide.
  1. 您需要回覆什麼？ 在一個來回中詢問使用者無法獨自解決、且需要從此人身上取得的具體決策或事實。當您有了一個具體清單，列出使用者必須能帶著去做或決策的事時，就完成了。
  1. Write the questionnaire. Draft questions aimed at the gap from steps 1–2, following the Document structure below. Write it to to-questionnaire-<slug>.md in the current directory (slug from the topic) and report the path. Done when the file exists and every item the user named in step 2 is covered by a question.
  1. 撰寫問卷。 起草針對第 1–2 步缺口的問題，遵循下方的文件結構。將它寫到目前目錄的 to-questionnaire-<slug>.md（slug 取自主題），並回報路徑。當檔案存在且使用者在第 2 步提出的每一項都被一個問題涵蓋時，就完成了。

Document structure

文件結構

Frame the document as a discovery questionnaire: the user lacks context, the recipient holds it. Order questions most-important-first — async means you may only get one pass — and group them under ## headings by theme once there are more than a handful. Write it using the template below.

將文件框定為一份發現問卷：使用者缺乏脈絡，收件人握有它。以最重要的優先排序問題 — 非同步意味著您可能只有一次機會 — 當問題超過幾則時，按主題分組在 ## 標題下。使用下面的範本撰寫。

Purpose: why this questionnaire exists and the decision riding on it.

From: — To: — How your answers will be used:

Context

One paragraph orienting a recipient who wasn't in the user's head. Enough to answer well, not a page.

How to answer

Deadline and rough effort. Partial answers and "I don't know" are useful — flag anything you're unsure of rather than skipping it.

One ## section per theme. Under each, its questions, most-important-first. Every question is one idea — never compound — with an answer stub directly beneath, and a one-line why this matters only where the question could be misread or invite a throwaway answer.

What load is the system expected to handle at launch?

Why this matters: it decides whether we provision for burst traffic now or defer it.

Anything else?

A closing catch-all: anything we didn't ask that we should know?

📖 教學解說

to-questionnaire 解決的是知識在別人的腦子裡的情境。你做了一個功能的 grill，但某些關鍵決策取決於一個你聯絡不上的人（PM、設計師、法務）。這個技能幫你寫一份問卷，寄給那個人填，然後把答案帶回 grill 或 to-spec。

關鍵設計：質詢的是寄送，不是主題。Agent 只訪問你「寄給誰、需要什麼回覆」——因為這些你總是能回答。問卷的問題針對「收件人知道但你不知道」的缺口。

💡 Worked Example

情境：你要做 CSV 匯出，但匯出的欄位隱私規範由法務決定。

  1. 呼叫 /to-questionnaire "CSV 匯出的欄位隱私規範"
  2. Agent 問：「寄給誰？」→ 你：「法務的王小明」
  3. Agent 問：「你需要他回答什麼？」→ 你：「哪些欄位可以匯出、哪些需要脫敏」
  4. Agent 產出問卷：`to-questionnaire-privacy.md`，包含：Context（專案背景）、問題（按主題分組）、Anything else
  5. 你把問卷寄給王小明 → 他填完回覆 → 你把答案帶回 grill

⚠️ 常見錯誤

  • 問卷問題太廣——「你覺得隱私方面有什麼問題？」太模糊。要具體：「以下哪些欄位需要脫敏？」
  • 訪問 agent 關於主題——Agent 應該訪問你關於「寄送」，不是關於「CSV 隱私規範」。你可能不懂隱私規範，但你知道誰懂。
  • 問卷沒有 Context——收件人不在你的腦子裡。問卷需要一段背景說明，讓他們能好好回答。
  • 問卷沒有截止時間——非同步問卷很容易被拖延。加一個 deadline。

✅ 練習 / 驗收清單

  • □ 問卷有 Context 區段（讓收件人能好好回答）
  • □ 問題具體且按主題分組
  • □ 有截止時間和粗略 effort 說明
  • □ 每個問題都對應到「收件人知道但你不知道」的缺口
  • □ 有「Anything else」收尾的包羅萬象問題

🚀 進階真實情境 Worked Example

情境：你的「訂閱制改版」卡在一個決策——既有會員的折扣該怎麼轉移。這個問題只有營運主管知道答案，但他下週才回國。

  1. 呼叫 /to-questionnaire "既有會員折扣轉移到訂閱制的規則"。
  2. Agent 質詢寄送：「寄給誰？」→ 你：「營運主管（負責既有會員權益）」。「你需要他回答什麼？」→ 你：「(1) 折扣是否延續 (2) 延續多久 (3) 新訂閱與折扣能否疊加」。
  3. Agent 依缺口設計問題：主管掌握的是「會員權益的歷史承諾」，你缺的是「轉移規則的決定權」——問題瞄準「我們能改動哪些既有承諾」這個你無從知道的邊界。
  4. 問卷結構：Context（一段話說明改版背景與既有折扣承諾）、主題分組（折扣延續／時間窗／疊加規則）、每個問題一個想法＋作答欄位＋只有易誤讀時才加「為何重要」。
  5. 寄出後主管填回：折扣延續一年、新舊不疊加。你帶著答案回到 /grill-with-docs，把「折扣轉移規則」寫進 CONTEXT.md。

設計決策：本例的關鍵是「寄給誰」的判斷影響問卷的專業深度——營運主管不需要（也不該）被問技術細節，他要回答的是「商業承諾」問題。若你誤把問卷寄給工程師，會拿到技術可行性的回答，卻仍然不知道「該不該延續折扣」。

🔬 深入原理擴充

to-questionnaire 是 grill 的非同步變體。grill 假設「能做決策的人就在對話裡」；to-questionnaire 處理的是「能做決策的人在別處、且不在場」。因此它的設計目標從「磨利思考」變成「最小化來回次數」——非同步意味著你可能只有一次機會，所以問題要按重要性排序、每題只問一件事、並明確給出「不知道也很有用」的許可。

「質詢的是寄送，不是主題」這個原則來自一個洞察：使用者對主題的無知不是問題，對寄送的無知才是。你不知道折扣轉移規則，但你一定知道誰知道——所以 agent 只訪問你能答的（寄給誰、需要什麼回覆），再從「收件人知識與你的需求之間的缺口」反推問題。

陷阱案例：很多人把問卷當成「知識測驗卷」，於是在 Context 裡塞滿專案背景、把每個問題都加上「為什麼重要」、還問「你覺得這個功能該不該做」這種開放式問題。真相是：問卷是「引產」工具，不是「傳教」工具——收件人握有知識，問卷的任務是把知識引出來。Context 只要「足以回答」的一小段；「為什麼重要」只在問題可能被誤讀或引來敷衍時才加；開放式大哉問（「該不該做」）把決策責任推回給不懂的人，等於沒問。

🩺 診斷式疑難排解表

症狀可能原因解決方案
收件人答非所問問題太開放或沒按主題分組每題只問一件事、按主題 ## 分組、最重要的排前面
收件人說「這我看不懂」Context 太長或沒寫給「不在你腦中」的人Context 只留一段必要的背景；用收件人領域的詞彙描述
問卷拖了一個月沒回沒有截止時間與努力說明在「How to answer」寫明 deadline 與預估時間，並允許部分回答
問題含兩個以上想法複合問題，收件人無法一次答拆成多題，每題單一想法＋作答欄位
回覆不完整，關鍵決策仍缺第 2 步「需要什麼回覆」沒收集完整發問卷前先列出「必須能帶著去決策的清單」，確保每項都被一題涵蓋

🏆 進階挑戰題

  1. 缺口分析：你要設計一個「從 SQLite 遷移到 Postgres」的問卷，對象是負責舊系統的資深 DBA。列出收件人知道但你不知道的三個知識區塊，並各設計一個精準問題。
  2. 複合題拆分：把「這個系統的流量高峰是什麼時候、為什麼會高峰、我們該不該先做快取」拆成符合「一題一想法」的三個問題，並排序。
  3. 非同步設計：你的問卷只有一次來回機會。說明你怎麼用「最重要的優先＋部分回答許可＋Anything else 收尾」三道防線，確保即使收件人敷衍也能拿到最有價值的資訊。
