Test-Driven Development

測試驅動開發

TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop. Every section applies on every cycle — consult them before and during the loop, not after.

TDD 就是紅 → 綠的迴圈。本技能是讓這個迴圈產出值得保留之測試的參考文件：什麼是好測試、測試放哪裡、反模式，以及迴圈的規則。每個章節在每個循環都適用——在迴圈之前和之中查閱它們，而不是事後。

When exploring the codebase, read CONTEXT.md (if it exists) so test names and interface vocabulary match the project's domain language, and respect ADRs in the area you're touching.

探索程式碼時，先讀 CONTEXT.md（如果存在），讓測試名稱和介面詞彙符合專案的領域語言，並尊重你要觸及區域中的 ADR。

What a good test is

什麼是好測試

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification — "user can checkout with valid cart" tells you exactly what capability exists — and survives refactors because it doesn't care about internal structure.

測試透過公開介面驗證行為，而不是實作細節。程式碼可以完全改變；測試不應該。好測試讀起來像規格說明——「使用者可以用有效的購物車結帳」確切告訴你存在什麼能力——而且能安然度過重構，因為它不在乎內部結構。

See tests.md for examples and mocking.md for mocking guidelines.

範例見 tests.md，模擬指引見 mocking.md。

Seams — where tests go

接縫——測試放哪裡

A seam is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

接縫是你測試所處的公開邊界：你在那裡觀察行為而不伸進內部。測試放在接縫，絕不對著內部。

Test only at pre-agreed seams. Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything — agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

只在事前約定的接縫上測試。 寫任何測試之前，先寫下將被測試的接縫並與使用者確認。不會在未確認的接縫上寫測試。你不可能測試一切——事先約定接縫，就是讓測試心力落在關鍵路徑與複雜邏輯上，而不是每個邊緣案例。

Ask: "What's the public interface, and which seams should we test?"

問：「公開介面是什麼，我們該測試哪些接縫？」

When the shape of that interface is itself in question — how deep the module is, where the seam belongs, what the interface should expose — use the /codebase-design skill for the vocabulary. It is the shared source of the module, interface, depth, seam, adapter, leverage and locality terms, and it is a reference to consult, not a session to run.

當那個介面的形狀本身有疑問時——模組要多深、接縫該放哪裡、介面該暴露什麼——用 /codebase-design 技能取得詞彙。它是模組、介面、深度、接縫、轉接器、槓桿收益與局部性這些術語的共同來源，而且是要查閱的參考文件，不是要執行的會話。

Anti-patterns

反模式

  • Implementation-coupled — mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.
  • Tautological — the assertion recomputes the expected value the way the code does (expect(add(a, b)).toBe(a + b), a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth — a known-good literal, a worked example, the spec.
  • Horizontal slicing — writing all tests first, then all implementation. Bulk tests verify imagined behavior: you test the shape of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in vertical slices instead — one test → one implementation → repeat, each test a tracer bullet that responds to what the last cycle taught you.
  • 耦合實作細節——模擬內部協作者、測試私有方法，或透過側通道驗證（查資料庫而不是用介面）。特徵：重構時測試壞掉，但行為沒有改變。
  • 同義反覆——斷言用跟程式碼相同的方式重新計算期望值（expect(add(a, b)).toBe(a + b)、用手以同樣方式導出的快照、跟自己比較的常數），所以它依構造而通過、永遠不會與程式碼意見不合。期望值必須來自獨立的真實來源——已知良好的常數、實際算過的範例、規格。
  • 水平切片——先寫全部測試，再寫全部實作。大量測試驗證的是_想像中_的行為：你測試的是東西的_形狀_而不是使用者可見的行為，測試對真實變動變得不敏感，而且你在理解實作之前就承諾了測試結構。改用垂直切片——一個測試 → 一個實作 → 重複，每個測試都是一顆回應上一循環所學的曳光彈。

Rules of the loop

迴圈的規則

  • Red before green. Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.
  • One slice at a time. One seam, one test, one minimal implementation per cycle.
  • Refactoring is not part of the loop. It belongs to the review stage (see the code-review skill), not the red → green implementation cycle.
  • 先紅後綠。 先寫失敗測試，然後只寫足以讓它通過的程式碼。不要預期未來的測試或加投機性的功能。
  • 一次一個切片。 每個循環一個接縫、一個測試、一個最小實作。
  • 重構不是迴圈的一部分。 它屬於審查階段（見 code-review 技能），不屬於紅 → 綠的實作循環。

📖 教學解說

TDD 的核心不是「先寫測試」——而是用測試驅動設計。紅-綠循環的每一輪都在問一個問題：「這個介面該長什麼樣子？」測試是問題，程式碼是答案。如果你發現自己在寫一大堆測試才開始寫實作，你可能掉進了「水平切片」的陷阱。

「接縫」是 TDD 最被低估的概念。接縫不是「你想測什麼」，而是「你能從外面觀察到什麼」。好接縫的特徵：從外部可觀察、不暴露內部結構、重構時不會斷。壞接縫的特徵：需要 mock 內部狀態、測試私有方法、依賴特定實作。

💡 Worked Example

垂直切片的 TDD 循環：

  1. 紅：describe('Cart') → it('calculates total with tax') → expect(cart.totalWithTax()).toBe(110) → 失敗（Cart 不存在）
  2. 綠：建立 class Cart，加 totalWithTax() 方法回傳 this.subtotal * 1.1 → 通過
  3. 紅：it('applies discount before tax') → expect(cart.withDiscount(0.1).totalWithTax()).toBe(99) → 失敗
  4. 綠：加 withDiscount() 方法 → 通過
  5. 重複：每次只加一個行為，確保測試先紅再綠

注意：每個循環都在同一個接縫（Cart 類別的公開介面）上操作，從不需要改測試結構。

⚠️ 常見錯誤

  • 水平切片——先寫全部測試再寫全部實作。這會讓你測試「想像中的行為」而非真實行為，測試對真實變動變得不敏感。
  • 同義反覆——expect(add(a, b)).toBe(a + b)。期望值必須來自獨立的真實來源：常數、規格、手動算過的範例。
  • 在迴圈中重構——重構屬於 review 階段（code-review），不屬於紅-綠循環。迴圈的規則是先紅後綠、一次一個切片。
  • 沒有確認接縫就開始寫測試——接縫必須事先與使用者確認。否則你可能在錯誤的抽象層級上測試。
  • 忽略 CONTEXT.md 的詞彙——探索程式碼時先讀 CONTEXT.md（如果存在），讓測試名稱符合專案的領域語言。

🚀 進階真實情境 Worked Example

情境：你要在既有購物車系統加「優惠券可疊加會員折扣」的功能，接縫是 calculateTotal(cart, coupons)。

  1. 確認接縫：spec 指定公開函式 calculateTotal(cart, coupons): Price，既有測試檔已有 calculateTotal 的 prior art。與使用者確認後開始。
  2. 垂直切片 1：it('合併多張優惠券的折扣') → 紅。建立最小實作：coupons.reduce((acc, c) => acc - c.discount, subtotal) → 綠。
  3. 垂直切片 2：it('折扣不低於零') → 紅。加 Math.max(0, ...) → 綠。
  4. 垂直切片 3：it('會員折扣與優惠券順序不影響結果') → 紅。把折扣計算改成「先套百分比再套固定額」，確保交換律成立 → 綠。
  5. 重構留到 review 階段：切片完的程式碼可能有重複的 Math.max 段落，但迴圈的規則就是「先紅後綠、一次一個切片」——重構不屬於紅綠循環。

設計決策：第三個切片（交換律）是最容易被跳過的一步——初學者常先寫「折扣順序敏感」的實作，測試全綠就以為完成。但「順序敏感」正是這類功能的隱形 bug 來源。TDD 的價值不是「有測試」，而是每一片測試都在用公開介面逼你定義行為契約。

🔬 深入原理擴充

「紅綠循環」是 Kent Beck 經典 TDD 的形式化，但本技能做了兩個關鍵延伸：接縫（seam）與反模式。接縫概念來自 Michael Feathers——它是「你可以改變行為而不修改那行的地方」。在 TDD 中，接縫決定「測試貼在哪一層」：接縫越高，測試越接近使用者行為、越耐重構；接縫越低，測試越快但越容易耦合實作。

三種反模式（耦合實作、同義反覆、水平切片）對應三個不同的失敗時刻：耦合實作讓測試在重構時斷（脆），同義反覆讓測試永遠不會斷（無用），水平切片讓測試在動手前就承諾錯誤結構（誤導）。三者都不是「測試寫錯」這種小事——它們是「測試的設計」層次的錯誤，無法靠改測試內容修好，只能重寫測試的意圖。

陷阱案例：很多人以為「期望值從『函式自己』拿就夠了」，於是用 expect(add(a,b)).toBe(a + b) 或「先實作、再讓測試引用實作結果」的方式寫測試。這就是同義反覆——期望值來自實作本身，測試與程式碼永遠不會意見不合，測試形同虛設。真相是：期望值必須來自獨立的真實來源——手算的範例（toBe(110) 的 110 是你自己算的）、規格裡的數字、已知良好的常數。若你發現測試「必然通過」，不是測試成功了，是測試失效了。

🏆 進階挑戰題

  1. 接縫分級：一個「訂單結帳」功能，接縫可以是「計算函式」「service 方法」「HTTP endpoint」。分析三者各自的優缺點，並說明你會在什麼情境下選哪個。
  2. 反模式辨識：判斷下列測試各犯了哪種反模式：（a）expect(service.calculate(x)).toBe(x * 2)（b）mock 了 repository 並斷言「被呼叫過」而不是結果（c）先寫 40 個測試再寫實作。並提出修正。
  3. 獨立來源設計：一個「依匯率轉換貨幣」的功能，匯率來自外部 API。設計一個測試，它的期望值不來自實作、不依賴網路，仍能驗證「轉換正確」。

🏗️ ① 專案級端到端 Worked Example

專案情境：你要為一個「購物車結帳」功能建立完整的 TDD 測試套件。

  1. 先跑 /codebase-design 定義接縫：公開函式 checkout(cart, paymentMethod): Order，這是唯一的測試入口。
  2. 垂直切片 1：it(' calculates total') → 紅。建立 Cart class，加 total() → 綠。
  3. 垂直切片 2：it('applies discount') → 紅。加 withDiscount() → 綠。注意：期望值（toBe(90)）是你手算的，不是從實作拿的。
  4. 垂直切片 3：it('rejects invalid payment') → 紅。加 error handling → 綠。
  5. 全部切片完成後，跑 /code-review 確認沒有反模式（耦合實作、同義反覆、水平切片）。

關鍵：TDD 的價值不在「有測試」，而在「每一片測試都在用公開介面逼你定義行為契約」。期望值來自手算，不來自實作。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能TDD 的測試執行時間會隨著測試數量成長。紅-綠循環中，只跑當前切片的測試（it.only），不是全部——這讓循環保持快速。
品質測試的品質指標：是否能在重構時存活（不耦合實作）、是否在 bug 時斷（不同義反覆）、是否反映使用者行為（不描述內部實作）。
安全TDD 的測試是防禦 regression 的第一道關卡——但測試本身也可能有安全漏洞（例如 mock 了錯誤的依賴、測試中 hardcode 了 password）。確保測試本身是安全的。
