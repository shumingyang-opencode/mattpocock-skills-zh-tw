📖 教學解說

學習路線把 35 個技能分成 L0–L4 + 支援層 + 詞彙層 + 雜項 + 進行中。核心邏輯是「先佈場地、再搞清楚要做什麼、再規劃、再執行、再收尾」。每一層都建立在前一層的基礎上——你不會在 L1 就跳到 L3。

關鍵概念：支援層和詞彙層隨時可翻。它們不屬於主流程的任何一個階段，而是跑在底下的基礎。domain-modeling 和 codebase-design 是「詞彙層」——它們提供共同語言，讓其他技能能正確溝通。research、teach、wizard 是「支援層」——隨時可以用，不一定要在主流程中。

✅ 練習 / 驗收清單

  • □ 能畫出 L0–L4 各層的技能清單
  • □ 知道支援層和詞彙層「隨時可翻」的意思
  • □ 知道 domain-modeling 和 codebase-design 屬於詞彙層
  • □ 知道 L0（setup）是所有工程流程的前置條件

🚀 進階真實情境 Worked Example

情境：一位剛加入的工程師要獨立處理「把舊匯出功能升級成串流版本」的需求，這是他第一次走完整個學習路線。

  1. L0：先跑 /setup-matt-pocock-skills 佈好場地——追蹤器用 GitHub、標籤用預設五個、領域文件單一上下文。
  2. L1：從 /ask-matt 開始，被導向 /grill-with-docs。在 repo 中 grill「串流版本的保留行為有哪些」，決策寫進 CONTEXT.md。
  3. L2：grill 後發現這是多 session 工程 → /to-spec 收斂成規格，/to-tickets 拆成「串流骨架」「錯誤處理」「取消機制」三張曳光彈 ticket。
  4. L3：逐 ticket /implement（內部驅動 /tdd），中途用 /prototype 驗證串流在百萬筆資料下的記憶體行為，/handoff 來回搭橋。
  5. L4：全部實作完後 /code-review 雙軸審查，最後用 /resolving-merge-conflicts 把功能分支合回 main。
  6. 整個過程隨時翻詞彙層（/domain-modeling、/codebase-design）與支援層（/research）——前者提供語言，後者補知識。

設計決策：學習路線不是教科書流程，而是風險分層——L1 的 grill 把「做什麼」的風險在 L3 之前消掉；L2 的 tickets 把「範圍」的風險在寫 code 前消掉；L3 的 TDD 把「行為正確」的風險在交付前消掉。每一層的產物都是下一層的輸入，缺一層，風險就會累積到最後一次爆開。

🔬 深入原理擴充

學習路線的分層邏輯對應到不確定性的類型，而不是任務的難度。L1–L2 處理的是「需求不確定」（要做什麼、範圍多大），L3 處理「執行不確定」（行為是否正確），L4 處理「整合不確定」（合回主線是否破壞）。每個階段的技能剛好是消滅該階段不確定性的工具——這解釋了為什麼「跳過 grill 直接 implement」會失敗：不是因為工程師不努力，而是因為他把「需求不確定」帶進了「執行階段」，而執行工具（TDD）消不掉需求不確定。

對 AI coding assistant 而言，學習路線其實是上下文管理策略：L1–L2 的決策（CONTEXT.md、spec、tickets）都是「可序列化的狀態」，讓 L3 的每個 implement 能從乾淨的 context 開始。這就是 ask-matt 強調「步驟 1–3 保持同一個 context window」、之後每個 implement 重新開始的原因。

陷阱案例：很多人以為「學習路線是死板的順序，必須嚴格照走」，於是把「雜項」或「進行中」的技能也塞進主流程。真相是：L0–L4 是主流程的軸，支援層與詞彙層是隨時可翻的備選——遇到「需要查第三方 API 規格」就翻 /research，遇到「詞彙打架」就翻 /domain-modeling，它們不必也照 L1→L4 的順序。把備選技能硬塞進主流程順序，就像在高速公路的每一段路都要求換一次輪胎。

🏆 進階挑戰題

  1. 風險分層：說明「需求不確定、執行不確定、整合不確定」各由哪一層的哪些技能消滅，並舉一個「不確定性被帶錯階段」的真實失敗案例。
  2. 情境路由：五個情境（接手既有功能做小改、從零做一個新 SaaS 的付款系統、線上 P1 事故、想學一個新語言、外部 PR 湧入）各自從學習路線的哪一層／哪個工具切入？
  3. 上下文策略：為什麼 L1–L3 前半段要「同一 context window」、L3 的每個 implement 卻要「從乾淨 context 開始」？用上下文管理的角度解釋這個對比。
