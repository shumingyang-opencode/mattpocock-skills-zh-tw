Write a handoff document summarising the current conversation so a fresh agent can continue the work. Save to the temporary directory of the user's OS - not the current workspace.

撰寫一份交接文件，總結目前對話，讓一個全新的代理可以繼續進行工作。儲存到使用者作業系統的暫存目錄 — 而非目前工作區。

Include a "suggested skills" section in the document, which suggests skills that the agent should invoke.

在文件中包含一個「建議技能（suggested skills）」段落，建議代理應該呼叫的技能。

塗掉任何敏感資訊，例如 API key、密碼或可識別個人身分的資訊。

If the user passed arguments, treat them as a description of what the next session will focus on and tailor the doc accordingly.

如果使用者傳入參數，將它們視為下一個 session 將專注於什麼的描述，並據此調整文件內容。

📖 教學解說

handoff 解決的是多 session 工作的核心問題：下一個 session 怎麼從上次停下的地方繼續。它不是摘要——而是包含足夠上下文的交接文件，讓一個全新的 agent 能接手工作。

關鍵設計：交接文件不要重複其他產物已捕捉的內容。規格在 to-spec 裡、ticket 在 to-tickets 裡、ADR 在 docs/adr/ 裡。交接文件用路徑或 URL 引用它們，而不是把內容抄進來。這就是 write-great-skills 裡的 single source of truth 原則。

💡 Worked Example

情境：你在 session A 裡 grill 了「CSV 匯出」功能，現在要換到 session B 去做 prototype。

  1. 呼叫 /handoff "我要用 prototype 驗證 CSV 串流的效能"
  2. Agent 會產生一個交接文件，包含：
    • 目前進度：已完成 grill，CONTEXT.md 裡有所有決策
    • 建議技能：/prototype（因為要驗證效能）
    • 引用：CONTEXT.md 路徑、相關 ADR 路徑
    • 不重複：不會把 CONTEXT.md 的內容再抄一遍
  3. 交接文件存到暫存目錄（/tmp），不落進 repo
  4. 在 session B 裡，agent 讀取交接文件，從上次停下的地方繼續

⚠️ 常見錯誤

  • 交接文件太長——把所有對話內容都抄進來。交接文件是摘要+引用，不是逐字稿。
  • 重複其他產物的內容——規格、ticket、ADR 都有各自的家。交接文件只放引用。
  • 沒有建議技能——交接文件應該包含「下一個 session 該呼叫什麼技能」的建議。
  • 把交接文件放進 repo——它應該在暫存目錄。交接是暫時的，不是永久文件。

✅ 練習 / 驗收清單

  • □ 交接文件包含：目前進度、建議技能、引用（路徑/URL）
  • □ 沒有重複其他產物已捕捉的內容
  • □ 有塗掉敏感資訊（API key、密碼等）
  • □ 文件存在暫存目錄，不在 repo 裡
  • □ 下一個 session 能從交接文件順利接手

🚀 進階真實情境 Worked Example

情境：你在 session A 裡完成了 wayfinder 的地圖繪製，現在要把「接下來該解決哪張決策 ticket」的工作交出去，由另一個 agent 在平行 session 中處理 research 類的 ticket。

  1. 呼叫 /handoff "在平行 session 解決地圖上『確認第三方支付 API 的費率結構』這張 research ticket"。
  2. Agent 產生交接文件：目前進度（地圖已繪製，目的地「付款整合規格」已定案）、建議技能（/research、/domain-modeling）、關鍵引用（地圖 issue URL、payment 相關 ADR、docs/agents/issue-tracker.md 的工作流程）。
  3. 不重複：不會把地圖內文、ticket 全文抄進交接文件——那些是 single source of truth，引用就好。
  4. 塗敏：文件不含任何 payment API 金鑰或客戶資料，只留「如何取得」的指引。
  5. 交接文件存到暫存目錄。平行 session 的 agent 讀取後，依 /research 的流程啟動子代理，把發現寫到一次性 research/payment-fees 分支，並從 ticket 帶上下文指標。

設計決策：wayfinder 情境下的 handoff 要特別注意「claim」規則——交接文件必須寫明該認領哪張 ticket、認領後其他 session 要跳過它，否則兩個平行 session 會撞同一張票。這份文件同時也是 wayfinder「一個 session 只解決一張 ticket」的執行載體。

🔬 深入原理擴充

handoff 解決的是 AI coding 的核心成本結構：context window 是有限的、對話是無法延續的。一份好的交接文件本質上是「壓縮狀態的序列化」——把一個 session 的思考狀態編碼成另一個 session 可以反序列化的文字。它的品質決定下一個 session 是「接續工作」還是「重新開始」。

為什麼檔案要放暫存目錄而不是 repo？因為交接文件是過程產物，不是事實來源。事實來源是 CONTEXT.md、ADR、ticket——它們該進 repo。交接文件描述「現在到哪了、下一步做什麼」，這個資訊的生命週期很短，放進 repo 反而會沉積成過時文件。暫存目錄＋引用路徑的設計，強制交接文件保持「薄」：只載狀態差，不載全部事實。

陷阱案例：很多人以為「交接文件越完整越好」，於是把整個對話歷史壓縮成一份 3000 字的文件。真相是：交接文件不是逐字稿，是索引＋狀態差。完整內容已存在於 spec / ADR / ticket / commit，交接文件把它們複述一遍只是製造第二份真相來源——下一個 agent 讀到衝突時（文件 vs 原始檔），它該信哪個？正確做法是把「已捕捉的內容」用路徑引用掉，交接文件只保留「尚未落地的狀態」與「建議技能」。

🏆 進階挑戰題

  1. 寫一份交接文件：假設你剛完成一場 grill-with-docs（已有 CONTEXT.md 與兩份 ADR），要交給平行 session 做 prototype。列出交接文件的五個段落結構，並標出哪些內容「引用」、哪些「內文」。
  2. 敏感資訊處理：對話中包含一個資料庫連線字串、一位同事的全名與手機號、一段 API 回應。逐一說明該如何處理（保留／塗掉／改成指引）。
  3. 防撞車設計：wayfinder 情境下兩個平行 session 可能認領同一張 ticket。說明交接文件該寫進哪一條規則來避免這個問題，並解釋 wayfinder 的「claim」機制。

🏗️ ① 專案級端到端 Worked Example

專案情境：你在 session A 完成了 bug 診斷和修復方案，但時間到了，需要交接給 session B 繼續實作。

  1. 在 session A 結束前跑 /handoff，它會壓縮對話成交接文件：包含「已確認的根因」「修復方案的選項」「未完成的步驟」。
  2. 交接文件自動包含「阻塞項」：session B 需要哪些上下文才能繼續？（例如：「需要讀 src/payment/gateway.ts 的第 150-200 行」）。
  3. 在 session B 開始時，載入交接文件：新代理可以直接從「修復方案 A 的實作」開始，不需要重新診斷。
  4. 如果交接文件有遺漏，session B 可以跑 /research 補充——交接文件會標註「此處需要補充」。

關鍵：交接文件的價值不在「記錄所有事」，而在「記錄下一個代理需要知道的事」。太多上下文反而會淹沒重點。

⚡ ② 效能 / 品質 / 安全深度

面向實務考量
效能交接文件的大小直接影響下一個代理的 token 成本。理想大小：1-2 頁 A4，包含「已確認的事」「未確認的事」「下一步」三個區塊。
品質交接文件最常見的遺漏：「未完成的步驟」只列了「做了一半的 PR」，沒列「為什麼做一半」。下一個代理需要知道「卡在哪裡」，不只是「做到哪裡」。
安全交接文件可能包含敏感的 API key 或 token——確保在交接前清除或替換為 placeholder。交接文件不應該是 secret 的載體。
