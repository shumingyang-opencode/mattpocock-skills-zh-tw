Domain Modeling

領域模型

Actively build and sharpen the project's domain model as you design. This is the active discipline — challenging terms, inventing edge-case scenarios, and writing the glossary and decisions down the moment they crystallise. (Merely reading CONTEXT.md for vocabulary is not this skill — that's a one-line habit any skill can do. This skill is for when you're changing the model, not just consuming it.)

在設計過程中主動建立並磨利專案的領域模型。這是主動的紀律——挑戰術語、發明邊緣案例情境，並在術語定案的那一刻把詞彙表和決策寫下來。（光是讀 CONTEXT.md 來取得詞彙不是本技能——那是一行程式碼習慣，任何技能都能做。本技能是用於當你在改變模型，而不只是消費它。）

Create files lazily — only when you have something to write. If no CONTEXT.md exists, create one when the first term is resolved. If no docs/adr/ exists, create it when the first ADR is needed.

During the session

會話期間

Challenge against the glossary

對照詞彙表挑戰

When the user uses a term that conflicts with the existing language in CONTEXT.md, call it out immediately. "Your glossary defines 'cancellation' as X, but you seem to mean Y — which is it?"

當使用者使用的術語與 CONTEXT.md 中既有的語言衝突時，立刻點出來。「你的詞彙表把 'cancellation' 定義為 X，但你似乎指的是 Y——哪個才對？」

Sharpen fuzzy language

磨利模糊的語言

When the user uses vague or overloaded terms, propose a precise canonical term. "You're saying 'account' — do you mean the Customer or the User? Those are different things."

當使用者使用含糊或過載的術語時，提出精確的規範術語。「你說 'account'——你指的是 Customer 還是 User？那是不同的東西。」

Discuss concrete scenarios

討論具體情境

When domain relationships are being discussed, stress-test them with specific scenarios. Invent scenarios that probe edge cases and force the user to be precise about the boundaries between concepts.

當領域關係正在被討論時，用具體情境壓力測試它們。發明探索邊緣案例、迫使使用者對概念之間的邊界精確起來的情境。

Cross-reference with code

與程式碼交叉比對

When the user states how something works, check whether the code agrees. If you find a contradiction, surface it: "Your code cancels entire Orders, but you just said partial cancellation is possible — which is right?"

當使用者陳述某個東西如何運作時，檢查程式碼是否同意。如果發現矛盾，把它浮上檯面：「你的程式碼取消整個 Order，但你剛才說可以部分取消——哪個才對？」

Update CONTEXT.md inline

內嵌更新 CONTEXT.md

When a term is resolved, update CONTEXT.md right there. Don't batch these up — capture them as they happen. Use the format in CONTEXT-FORMAT.md.

當一個術語定案時，就地更新 CONTEXT.md。不要累積再一次處理——邊發生邊捕捉。使用 CONTEXT-FORMAT.md 中的格式。

CONTEXT.md should be totally devoid of implementation details. Do not treat CONTEXT.md as a spec, a scratch pad, or a repository for implementation decisions. It is a glossary and nothing else.

CONTEXT.md 應該完全不含實作細節。不要把 CONTEXT.md 當成規格、便條紙，或實作決策的倉庫。它是詞彙表，而且僅此而已。

Offer ADRs sparingly

斟酌提供 ADR

Only offer to create an ADR when all three are true:

只有三個條件都成立時，才主動提出建立 ADR：

  1. Hard to reverse — the cost of changing your mind later is meaningful
  2. Surprising without context — a future reader will wonder "why did they do it this way?"
  3. The result of a real trade-off — there were genuine alternatives and you picked one for specific reasons
  1. 難以逆轉——之後改變心意的成本是實際的
  2. 沒有上下文會令人驚訝——未來的讀者會想「為什麼他們要這樣做？」
  3. 真實取捨的結果——存在真正的替代方案，你基於特定理由選了其中一個

If any of the three is missing, skip the ADR. Use the format in ADR-FORMAT.md.

如果三個條件缺一，就跳過 ADR。使用 ADR-FORMAT.md 中的格式。

📖 教學解說

domain-modeling 的目標是建立共同語言。當團隊對「order」「user」「payment」這些詞的定義不一致時，所有溝通都會出問題。CONTEXT.md 就是這份共同語言的權威來源——它是一個詞彙表，僅此而已，不含實作細節。

關鍵機制：(1) 對照詞彙表挑戰——當使用者用的術語與 CONTEXT.md 衝突時，立刻點出來。(2) 磨利模糊語言——「account」到底是 Customer 還是 User？(3) 與程式碼交叉比對——如果程式碼的行為與詞彙表矛盾，浮現它。

💡 Worked Example

情境：團隊對「cancel order」的理解不一致。

  1. Agent 問：「你說 cancel order，是指取消整個訂單還是部分商品？」
  2. 你回答：「取消整個訂單」
  3. Agent 檢查程式碼：發現 cancel 函數只把 status 設成 cancelled，但沒有處理已出庫的商品
  4. Agent 點出矛盾：「你的程式碼只改了 status，但你說要取消整個訂單——已出庫的商品怎麼辦？」
  5. 你決定：「要加一個 inventory rollback 的步驟」
  6. Agent 更新 CONTEXT.md：「cancel order = 把 status 設為 cancelled + rollback 已出庫商品」

⚠️ 常見錯誤

  • CONTEXT.md 實作細節——CONTEXT.md 是詞彙表，不是規格。不該有「在 src/cancel.ts 裡……」這種內容。
  • ADR 太多——只有三個條件都成立（難以逆轉、沒有上下文會令人驚訝、真實取捨）才建 ADR。不然只會堆出一堆沒人讀的文件。
  • 不與程式碼交叉比對——詞彙表說「cancel = 完整取消」，但程式碼只改 status。這種矛盾不浮現 = 詞彙表不可信。
  • 術語衝突不立刻點出來——等衝突累積才處理 = 團隊會在錯誤的基礎上繼續建構。

✅ 練習 / 驗收清單

  • □ CONTEXT.md 只含詞彙表，不含實作細節
  • □ 術語衝突有立刻被點出來並解決
  • □ 模糊語言有被磨利（「account」→ Customer 或 User？）
  • □ 詞彙表有與程式碼交叉比對
  • □ ADR 只在三個條件都成立時才建立
  • □ 術語定案後有就地更新 CONTEXT.md

🚀 進階真實情境 Worked Example

情境：你的電子商務專案要新增「訂閱付款」，產品經理開口就說「訂閱就是一個會重複扣款的黑卡」。你發現 CONTEXT.md 已有「subscription」「billing cycle」「charge」三個詞。

  1. 挑戰模糊語言：PM 說的「黑卡」其實是「儲值卡」，與既有的 charge（向已建立的付款方式扣款）衝突。提出精確詞彙：「subscription 的 charge 是自動扣款；黑卡應正名為 wallet，是另一種付款方式」。
  2. 對照詞彙表挑戰：CONTEXT.md 定義 charge 為「一次性扣款，需使用者授權」。但訂閱的 charge 是排程自動執行、不需每次授權——定義衝突。點出來：「你要的是被授權過的 recurring charge，詞彙表需要加一筆」。
  3. 具體情境壓力測試：問 PM「訂閱到期但付款失敗時，訂閱狀態是什麼？是 cancelled 還是 pending？」PM 答「pending」。於是把 pending 加入詞彙表並定義清楚。
  4. 與程式碼交叉比對：程式碼的 Subscription 模型只有 active | cancelled 兩態，沒有 pending——矛盾浮現，這成為改 schema 的前置決策。
  5. 就地更新：在 CONTEXT.md 新增 recurring charge、wallet、pending 三筆；確認 cancelled 定義不變。以 ADR 記錄「訂閱狀態機加入 pending」這個難以逆轉的決策。

設計決策：本情境的關鍵是新功能帶進的術語會衝擊既有詞彙表。常見錯誤是「順著使用者的新詞彙建新功能」，導致同一個 charge 在系統裡有兩種意思。domain-modeling 的做法是先挑戰、再定義、最後才寫程式——詞彙衝突不解決，schema 與 API 的命名就會互相打架。

🔬 深入原理擴充

domain-modeling 的理論根基是 Eric Evans 的 Domain-Driven Design 裡的 Ubiquitous Language（通用語言）。核心主張：軟體裡最貴的溝通成本不是「寫程式」，而是「團隊對同一個詞的共識漂移」。當 cancel 在 PM 嘴裡、工程師 code 裡、客服系統裡指三種不同的東西，任何跨角色的溝通都要先翻譯——而翻譯正是 bug 的溫床。

CONTEXT.md 設計成「詞彙表，僅此而已」不是保守，而是刻意維持單一事實來源：如果它同時當規格、便條紙、實作決策倉庫，就會像 codebase-design 講的「sediment」一樣長出過時層，最後沒人敢信它。ADR 則負責「難以逆轉的決策」，兩者分工明確。

陷阱案例：很多人以為「把術語定義清楚」就是把字典抄進 CONTEXT.md——於是用一整段散文定義 order，甚至抄了「order 有 status 欄位」這種實作細節。真相是：詞彙表要定義「詞的意思」，不是「詞的實作」。`order 是顧客購買商品的請求` 是好的定義；`order 的 status 欄位存於 orders 表、值為 PENDING/PAID/CANCELLED` 是污染的定義——後者會隨 schema 改變而過時，讓整份詞彙表失信。

🏆 進階挑戰題

  1. 過載術語解析：團隊整天講「order」，但你發現它同時指「購物車結帳的請求」「已建立的訂單記錄」「電子郵件裡要出貨的包裹」。設計三筆詞彙表定義把它們拆開，並各舉一個使用情境。
  2. ADR 三條件：下列哪些該建 ADR、哪些該跳過？（a）選用 Postgres 當寫入模型（b）表單欄位用 camelCase 命名（c）訂單狀態機加入 pending 態。逐項用三條件判斷。
  3. 矛盾浮現：詞彙表定義「cancellation 是完整取消訂單」，但程式碼的 cancelOrder 只把 status 設成 CANCELLED、不處理已出貨商品。寫出你作為 agent 會對使用者說的一句話。
